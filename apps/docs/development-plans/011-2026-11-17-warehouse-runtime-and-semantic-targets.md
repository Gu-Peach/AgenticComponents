# 011：升降台虚拟交接、滑轨定位与仓储场景运行方案

日期：2026-11-17。

状态：已接入仓储候选仿真。本文已归档到 apps/docs/development-plans；下面保留原方案，实施结果与用户后续确认见第 11 节。

## 1. 目标与已确定的选择

在已完成的 S07 节点绑定与设备声明之上，实现可复用的升降台、直线滑轨和仓储服务，使有限物料能够从输送线进入升降平台、存入格位，再经另一侧升降平台送至出口。

按以下顺序实施，不跳过单设备验证直接堆叠整场逻辑：

1. **统一契约**：确定接料、放料载荷及虚拟交接模式，调整 Handler 条件，明确平台承载点与轴坐标。
2. **实现基础运行能力**：直线轴运动、虚拟物料转移、承载绑定及停止处理。
3. **实现设备模块**：升降台、滑轨和仓储服务分别验证，再测试滑轨搭载升降台的组合运动。
4. **扩展场景装配并调整 DSL**：先跑通“输送线 → 升降台 → 一个格位 → 出口”的单件流程，再恢复四件任务。
5. **验证通用性**：更换实例名称、位置和格位配置，检查同一套实现仍可运行；同时回归 S01。

本轮实现阶段采用以下确定方案：

- 接料、放料均使用**短距离直线移动**；保持物料姿态，不模拟货叉伸缩，不采用瞬移。
- 动画、物理状态和库存共用运行证据。渲染只读取快照，物料位置由统一物理后端管理。
- 滑轨是单自由度直线轴，方向定义在设备局部坐标系。场景实例可以沿 X、Z 或其他已声明的水平方向放置。
- 生产 DSL 优先引用具名位置，例如 `C1.exit`、`STORE.slot1`；轴位移由几何解析器计算。数值轴目标继续保留，用于标定和调试。
- 本轮只支持目标在一次请求期间静止的定位和交接。Agent 的实时查询及提出目标预留接口；持续追踪移动目标属于后续独立能力。
- 先采用顺序运动、顺序交接。多轴同步与入出库并行可以后续扩展，不是本轮验收前提。

## 3. 阶段一：统一契约

### 3.1 升降台对外行为

| 行为 | 拟定输入 | 完成语义 |
| --- | --- | --- |
| accept_material | 类型化 payload：material、source；目标隐含为本平台 load_anchor | 指定物料到平台承载位置，承载关系建立，来源与平台占用更新 |
| release_material | 类型化 payload：material、target；来源隐含为本平台 | 物料由目标实际接收，平台承载解除，库存提交 |
| lift_to_level | 保留 move_to_level，单位 m，参考系由契约明确 | 平台高度到位、停稳、载荷有效 |
| lift_to_location | 新增具名 target 引用，通过对接解算得到高度 | 对应本请求冻结的目标高度到位并停稳 |
| hold_lift | 停止请求 | 已减速停稳且收到相关回执，保留载荷 |

接料和放料统一调用 MaterialTransferService；现有 transfer_material 在迁移期作为薄兼容入口，根据本机端点解析为接料或放料。两个端点均非本平台、均为本平台或路线未声明时拒绝，不另写一套转移逻辑。没有本轮实现的其他可选升降行为继续保留 pending 状态。

配置新增虚拟交接 profile（字段名拟定）：

```json
{
  "transfer": {
    "mode": "virtual_linear",
    "orientation_policy": "preserve",
    "speed_param": "transfer_speed_mps",
    "acceleration_param": "transfer_accel_mps2",
    "max_distance_param": "transfer_max_distance_m",
    "load_anchor_ref": "platform.load_anchor",
    "completion_evidence": "pose_support_ownership_and_request"
  }
}
```

速度、加速度、最大转移距离、位置误差、停稳阈值、目标接触检查须有单位和来源。虚拟交接是明确的模拟能力，不能被输出为已经验证实体货叉行程或碰撞规划的证据。

移除本 profile 对真实 Handler 伸缩与收回观测的依赖；Handler 保留为模型部件。以“虚拟交接未活动、物料归属明确”作为轴运动互锁。未来实体 Handler profile 可以有自己的伸缩与收回条件，二者不可同时写入同一物料。

### 3.2 平台承载点与高度参考

区分以下位置：整场原点、轨道根、升降机根、平台关节原点、平台承载面中心、物料原点/质心。截图中的 `(0,0,0)` 不能自动充当平台承载点。

平台承载点定义在平台局部坐标中，并声明承载面法向和有效支承区域。当前世界位置由轨道和升降组合变换得到。物料目标位姿依据物料底面/支承形状计算：立方体中心原点且直立时可以加半高；一般模型必须使用其原点偏移与形状外廓，不能普遍使用半高公式。

保持 lift_to_level 的既有“设备基准高度”含义，明确它与内部竖直轴位移 q_l 的转换。`q_l=0` 对应 GLB 记录的参考平台位姿；参考位姿不等于已完成硬件回零。平台实际高度 = 基准高度 + 已声明的静止偏移 + q_l 的轴向分量。不得将世界 Y 坐标直接作为局部行程。

### 3.3 滑轨坐标模型

设备契约定义一维定位能力和参数；实例模型定义几何及轴配置（字段为拟定结构）：

```json
{
  "motion": {
    "kind": "prismatic",
    "axis_frame": "rail_local_m",
    "axis_local": [1, 0, 0],
    "zero_pose_ref": "mounted_device_rest",
    "limits_ref": "travel_limits",
    "mounted_device": "L1"
  }
}
```

同一局部 X 轴模型绕竖直方向旋转后可以沿世界 Z 运动；模型本身也可以显式声明局部 Z。实现读取轴向量和刚体变换，不按世界 x/z 分支，不按 T1/T2 或场景名称分支。首版支持水平滑轨和竖直升降，不推断任意倾斜轨道的重力保持能力。缩放须在编译时规范化为米制；不允许未处理的非均匀缩放影响轴长度或限位。

方向与零点是固定的运动学定义；每次任务的目标位移可由场景计算变化。对同一场景快照、目标、参数和策略，解算结果应可重放。

保留 `move_to_position(position_m)` 的标量轴目标语义；新增 `move_to_location(target)` 的具名位置语义。两者走同一轴执行器，均受相同限位、速度、资源和停止规则约束。本轮契约版本建议将 linear_rail 从 1.0.0 升到 1.1.0，lift_table 从 S07 的 1.1.0 升到 1.2.0；具体版本在实现时按最终兼容范围锁定，未知版本拒绝。

### 3.4 仓储服务

保留格位容量、预留、存入、取出、撤销预留和查询语义；货架几何保持静态。库存状态至少区分 empty、reserved、occupied，以及记录在独立转移账本中的 in_transfer 状态。

库位选择由任务或调度策略明确提出，首版使用固定 job.slot，不启用隐式 first_available 替换。选定格位与实际接受预留是不同事件。预留使用现有资源授权入口，或显式服务行为入口；一个流程只选定一种预留入口，避免 DSL 和转移服务重复申请。

仓储服务提交库存的依据是转移执行器的关联证据，不能在调用 accept/release 时提前宣告存取完成。原有整数信号 ID 与字符串格位引用使用显式登记映射。

**本阶段出口**：契约版本、payload、条件表达式、参数单位、平台坐标、运动轴、资源规则及独立验收语义可静态检查；虚拟模式不再依赖实体 Handler 回执。

## 4. 阶段二：基础运行能力

### 4.1 moveTool 的复用方式

当前 PhysicsPort.moveTool 的 Jolt 实现明确要求 `motionType=kinematic` 且 `role=tool`。因此不能直接把 dynamic/material 的物料 ID 传入，也不能将升降平台临时伪装成工具。

推荐复用路线：

1. 为交接服务创建无可视网格的虚拟运动学夹持点，按合法 tool 类型注册，碰撞策略明确。
2. 初始夹持点位于物料当前位姿，建立固定约束时保留物料姿态与偏移。
3. 生成直线轨迹，每个固定 tick 计算下一步夹持点位姿，再调用现有 moveTool。保持运动轨迹共线，用时间缩放约束速度和加速度。
4. 由固定约束带动物料的动态刚体；真实世界读数决定是否到位，不由轨迹计时直接产生 done。
5. 到达目标后完成接触、几何包含、停稳和承载关系切换，提交交接回执。

现有 moveTool 只是一帧的底层运动原语，不包含整段插值、限速、物料身份、资源、库存或停止状态机。GraspService 绑定了机器人配置和捕获半径，不能整套直接用于升降台；可复用更底层的固定约束能力，并建立独立的转移服务。

升降平台和滑轨挂载支承使用拟新增的通用 moveKinematicBody 接口。其底层可与 moveTool 共享 KinematicToolDriver 的运动代码，入口继续按角色和运行所有权检查，不向业务层暴露任意刚体写坐标。

### 4.2 转移与承载状态机

建议状态：prepared → accepted → transferring → settling → committed。取消/失败进入 stopping，随后根据实际物料状态进入 stopped 或 attention_required。

- prepared：验证源物料身份、有效支承、目标容量、允许路线、最大距离、姿态兼容及直线路径可用；预检无物理副作用。
- accepted：冻结起点、目标及相关 revision，取得物料、源/目标位置和轴互锁资源，建立唯一转移所有者。
- transferring：虚拟夹持点沿直线移动。源实际空出后记录 departure，物料归属为 transfer，不同时占用两个库存。
- settling：验证目标接触与空间容纳，等待实际位姿和速度满足条件。
- committed：原子更新承载关系、库存和关联请求结果，释放临时转移资源。

接料完成后以显式平台承载绑定保证物料随轨道/升降组合运动。放料到静态格位或输送线后解除平台/临时工具约束，由目标支承管理物料。当前 carry 方法只接受 carrier 角色，releaseCarrier 是私有方法，且已有工具约束时禁止 carry；必须新增受控的约束切换操作，不能简单连续调用现有方法并假定成功。

约束切换在统一物理步边界执行，先验证新旧双方再提交；失败时保留原有效持有关系，不能产生一帧无主物料或双重驱动。库存与约束切换使用一致事务 ID，重复回执不得重复入库。

当前 hasSupport 会把载具绑定视为支承，交接终验应区分“真实接触/几何支承”和“虚拟绑定保持”，不得先绑住物料再用绑定本身证明目标已经接收。虚拟夹持点与本物料的碰撞可以按已有方式禁用；不得全局关闭物料与场景的碰撞。无法通过的直线路径应拒绝或失败，不自动穿过货架；暂不增加复杂绕障规划。

### 4.3 直线轴与组合位姿

增加 LinearAxisTrajectory/Runtime：支持有符号 q、速度/加速度限制、有限行程、到位容差和受控停止。可复用 JointTrajectory 的时间缩放公式；必须另行实现从当前速度停止，不能把原本从静止开始的轨迹直接用于中途重启。

统一组合关系：

`场景位姿 × 轨道基准 × 轨道平移(q_r) × 升降机装配偏移 × 升降平移(q_l) × 平台局部承载点`

一个组合位姿计算器生成相关刚体目标；轨道适配器提交 q_r，升降适配器提交 q_l，不能分别写同一个平台世界位姿。物理刚体和可视节点共用该结果，避免父子平移叠加两次。

升降机不能继续把整棵子树当作一个不会分动的刚体：需编译出移动机架与升降平台，Handler 在虚拟模式下按其所属平台保持原局部变换。每个网格唯一归属，平台与机架的刚体、可视绑定一一对应。

### 4.4 暂停、停止与重置

- 暂停冻结逻辑时钟、轨迹、约束与请求；继续使用原目标快照。
- 停止按当前速度减速，保留物料承载/虚拟夹持和格位预留，等待实际停止回执。
- 中途交接取消不报告目标交付成功。物料仍由虚拟夹持点持有且没有完成交接时进入 attention_required，保留当前位姿和资源以供恢复。
- 自动恢复/撤回不是本轮默认动作。增加明确的停止会话处置或“丢弃本次仿真并恢复初态”入口时，必须单独定义语义，不复用成功完成回执。
- 重置恢复原始层级、库存及刚体状态，释放本次会话资源；新会话生成新的 runId。

**本阶段出口**：基础测试证明限速、到位、支承切换、唯一所有权及取消保持。设备执行器不得另建或自行推进物理世界。

仓储服务始终参与观察与终验；没有显式仓储 invoke 时，不为每个格位创建主动运动循环。

组合验证至少覆盖：空载轨道移动、载物平台升降、载物整机沿轨道移动、交接期间轴命令被拒绝、停止后载荷保持。首版禁止同一组合的水平和竖直轴同时运动，但不限制未来以明确多轴协议扩展。

| 格位/输送接口位置、局部参考系、对接法向、允许交接距离和路线 | 场景位置与对接关系 |
| 要处理哪件物料、送往哪个位置、工步先后 | 任务与 DSL |
| 本次目标对应的轴坐标、解算误差、限位结果 | 运行目标解析器 |
| 选择目标、根据事件提出新任务或调整建议 | 未来 Agent/调度策略 |

位置只维护一份坐标来源：静态格位可以是设备局部坐标，移动对象位置由有效世界观测推导。GLB 网格中心只是几何线索；“可交接点”必须声明用途、接近侧和有效范围。货架两侧访问同一格位，可配置不同的对接关系，不复制两份库存身份。

### 6.2 从具名目标求轴位置

拟新增 LocationRegistry 与 DockingTargetResolver。后者读取一个冻结输入帧，解析目标端点、平台承载点、挂载关系和轴坐标，输出：目标身份、参考系/版本、q_r、q_l、虚拟交接端点、剩余间隙、校验结果和证据。

简单单轴定位示例：令世界单位轴向为 a，轴零点时被对齐参考点为 p0，解析后的该参考点目标为 p*，则：

`q_target = dot(a, p* - p0)`，`delta_q = q_target - q_current`。

同时计算不可由该轴消除的残差 `r = (p* - p0) - a * q_target`。只有满足所声明对接约束才允许执行，不能对任意目标投影后就宣布可达，也不能把超限 q 静默夹到限位。

仓储组合中，目标格位中心位于货架内部，平台中心位于货架外，两者允许保留用于虚拟交接的横向间隙。因此 p* 必须是**根据接近侧、平台偏移和允许交接距离解析出的平台对接位置**，不能直接把货架中心代入并强求整个平台进入货架。

对于水平滑轨 a 与竖直升降轴 b，求满足对接约束的 `p0 + a*q_r + b*q_l`。首版轴正交时使用解析投影，扣除已声明的装配/承载点偏移；逐项验证水平与竖直行程、剩余交接间隙、支承和直线路径。任意斜轴、多解搜索或复杂避障不在首版范围。

对“面对某物料接料”的请求，应依据物料身份和来源区域解析其当前有效支承位置，而不是仅用来源输送线出口的名义中心。若名义位置足以保证有限交接距离，可直接使用其既定对接点；两种策略须显式声明，不由行为名猜测。

### 6.3 DSL 使用方式

下例为**拟议新契约调用**，尚不能由当前运行工厂执行。语法沿用现有 invoke/payload；新增行为、location_ref 参数及其运行绑定必须在实施时一起注册。

```python
# 平台先与入料端对齐。具体轴数值由场景几何解析。
invoke('rail_to_infeed', T1, 'move_to_location', target=C1.exit)
invoke('lift_to_infeed', L1, 'lift_to_location', target=C1.exit)
invoke('accept', L1, 'accept_material',
       payload=payload('L1.accept_material', material=job.material, source=C1.exit))

# 工艺只选目标格位，平台接近位置与短距交接终点由对接关系决定。
invoke('rail_to_slot', T1, 'move_to_location', target=job.slot)
invoke('lift_to_slot', L1, 'lift_to_location', target=job.slot)
invoke('store', L1, 'release_material',
       payload=payload('L1.release_material', material=job.material, target=job.slot))
```

同一对接过程的水平、竖直定位和交接应使用一致的目标版本。首版目标静止，交接前仍复核目标位置与实际轴状态；若目标发生变化，不悄悄沿旧目标交接，应停止该次准入并返回需要重新定位的诊断。后续动态任务可引入显式对接解算 ID，在多个动作中关联同一冻结解算。

现有 `move_to_position(position_m=...)` 与 `lift_to_level(move_to_level=...)` 保留数值模式。生产流程迁移后，不再需要为每个格位重复维护 rail_key/height_key；维护轴零点、限位、承载点和格位坐标即可推导目标。确有实测偏差时，在对接标定中保存修正和来源，而不是把偏差散落到 DSL。

## 7. 阶段四：场景装配与单件/四件流程

### 7.1 编译与运行数据

扩展 CompiledSceneRuntime，表达独立物料 jobs、轴装配、运动学支承、位置/对接登记、库存服务与目标验收器。将当前载盘分拣能力与新增仓储能力拆成按配置和契约选择的 profile，保留统一调度器、时钟、信号和世界，不按 S07 字符串特判。

具体工作：

- 放开有物料但 pallet_count=0 的合法任务；验证数量、身份和目标，不降低独立验收要求。
- 实现 F1 有限物料供给与出口接收。不能以无限复制物料代替四件登记身份。
- 补齐 M01–M04 的物料形状、质量、可视资源与初态。可以采用显式声明的仿真箱体，但不能从截图擅自推定尺寸、质量。
- 配置 C1/C2 的支承面、流向、entry/exit、平台承载点与有效轴限位。几何可推导项附证据，不能自动确定的项保留阻塞。
- 注册新设备工厂、条件读数、资源集合、具名目标解析；保留数值标定入口时补齐 calibration 读取器及单位/未知值检查。
- 将 STORE 的静态支承与库存登记分开：格位占用不等于已创建物理支承。
- 初始稳定检查适应无托盘的物料供料，移除对第一盘 supply_confirmed 的单一依赖。
- 扩展可视桥，对轨道机架、平台、载荷和重置应用统一组合位姿。

### 7.2 单件先行

建立独立单件测试 fixture 和匹配目标，不修改正式四件 task-spec 来使测试通过。单件链路为：

`F1供料 → C1到位停稳 → T1/L1对接 → L1接料 → T1/L1格位定位 → L1放料入库 → T2/L2定位 → L2接料出库 → T2/L2出口对接 → L2放料 → C2输送/交付/停止`。

入库后必须先确认库存已提交，再允许出库。完成要求：正确物料曾进入指定格位，随后从该格位取出，最后收到 C2.exit 的有效交付回执；轴停止、平台无残留载荷、无活动请求与遗留临时预留。

### 7.3 恢复四件

保留 M01–M04 对应 STORE.slot1–4 和 C2.exit 的独立目标。先完成全部入库，再按订单逐件出库。正式 task-spec 保持独立，仓储事件逐物料记录：入库格位、提交 tick、出库 tick、最终出口和事务身份。

不复用“机械臂工具为空”作为唯一载荷判定：将该类终验分发到各设备的持有/承载状态提供者，验证升降平台和虚拟工具均无残留物料。旧 S01 的终验含义保持一致。

**本阶段出口**：单件和正式四件在真实 Jolt 世界运行成功，保存模型/输入哈希、请求轨迹、目标解算、交接与仓储事件、最终资源状态。界面准备成功不能代替整场验收。

## 9. 未来 Agent 实时场景接入

当前 SceneRuntimeController 已提供运行快照订阅，但还不是可直接给外部 Agent 使用的工具接口。后续可从同一快照/事件流导出物料位置、支承/持有者、轴状态、格位状态、目标版本和诊断。

Agent 可以根据当前任务选择格位、查询某个目标是否可达，或提出新的目标位置。建议调用统一目标解析接口取得 q_r/q_l 与证据，避免语言模型反复手算偏移。若 Agent 自行计算数值，同样必须携带参考系、单位、状态版本与目标身份并经过运行时复核。

目标生命周期建议为：

`读取快照 → 提出位置/任务 → 检查版本与质量 → 几何解算 → 原子授权重检 → 接受并冻结目标 → 执行 → 发布实际结果`。

静态作者文件、运行期位置观测、Agent 目标提案分别保存。当前运行锁继续保护工程文件，Agent 不在执行中改写 scene.json 或正在运行的 process.py。新提案保存在会话目标登记表中，接受后记录 targetId/revision/来源 tick/实际轴目标；传输协议还需定义去重 ID、有效期及拒绝原因。

对于已接受请求，物理循环每个 tick 执行冻结轨迹。Agent 不直接逐帧写物料坐标，也不因新观测到达就静默覆盖目标；需要改变目标时，在允许的工步边界提交新请求，或走取消、确认停止、重新规划流程。

“追踪正在运动的物体”需另行定义连续跟踪行为、延迟和更新频率、预测、失联策略及动态交接条件。首版可读取动态位置并在准入时取快照，但仅在端点停稳后交接，不把实时监听等同于连续运动控制。

本轮为此保留位置版本、状态质量、解算证据和事件接口，不以完整 Agent 平台接入作为 S07 基础运行的前置条件。
