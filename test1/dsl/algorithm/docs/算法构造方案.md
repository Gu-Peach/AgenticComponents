# 设备契约驱动的工艺执行路径验证：算法构造方案

版本：设计 0.1。日期：2026-11-01。

本方案承接 [研究点一定位](../../docs/method.md)，规定后续算法的文件组织、模块职责、输入输出和验证责任。当前已有 `src/acverify` 的显式验证器、状态约简、有限图 SMT 查询和测试，覆盖范围见 [实现说明](../README-method1.md)。下文目录保留目标架构，不代表直接符号编码、通用切片和局部摘要均已完成。场景与数据集详见 [数据集构建方案](数据集构建方案.md)。

## 1. 算法解决什么问题

给定候选工艺 P、设备和工艺契约 C、场景问题数据 E、环境假设 A、独立任务规格 G 以及性质集合 Q，构造有限状态转换模型并分析允许的执行路径。输出有边界的验证结论和可定位到工艺源码的路径证据。

核心问题包括：请求与反馈是否关联正确；何时允许执行、完成和释放资源；物料归属与预留是否一致；连续控制在退出时是否停稳；并行、分支、重复和异常情况下是否存在违例路径。目标可达、所有路径安全和有界响应分别求解。

本算法不负责生成最优工艺顺序、不做 IK/碰撞求解、不优化派工。算法可直接读取自定义符号场景，只要求语义实例、能力契约、状态转换及任务数据完整；不要求 GLB、图片、坐标或节点映射。GLB 和图片是可选的场景来源与后续展示材料，不能直接提供 `reachable=true`、设备前置条件或者真实反馈。空间条件若被使用，应作为明确外部假设；结论必须显示对这些假设的依赖。

## 2. 总体数据流与表示

```text
process.acp + environment + DeviceSpec + 能力适配
                    │
              解析 / 绑定 / 快速检查
                    ↓
          ProcessIR + BindingIR + source map
                    │       + 验证语义补充模型
                    │       + 初态 / 环境假设 / 时钟配置
                    ↓
          TransitionIR：控制器 × 设备 × 环境
                    │
     契约规则 + 独立 TaskSpec → PropertyIR
                    │
      初态可满足 / 触发可达 / 模型覆盖检查
                    ↓
     未优化基线 / 性质切片 → 有界路径求解
                    ↓
         完整模型重放 → 领域诊断与报告
```

建议研究原型采用 Python，复用已有前端和 JSON Schema 校验；求解后端通过接口隔离。首版同时保留小模型显式探索与 Z3 有界编码。Z3 用于判断逻辑公式可满足性，是算法组成部分，不能代替领域建模、性质设计与正确性论证。[Z3 官方说明](https://microsoft.github.io/z3guide/docs/logic/intro/)

各表示职责如下：

| 表示 | 内容 | 不放入的内容 |
| --- | --- | --- |
| BindingIR | 已解析设备、能力、参数、名义引用、授权继承、契约版本和事实提供者 | GLB 全部网格、尚未实现的动作代码 |
| TransitionIR | 有限状态变量、初态、带 guard/update 的阶段转换、环境输入、来源标签 | 求解器专属表达式对象 |
| PropertyIR | 性质 ID、类型、触发条件、公式、观察阶段、适用范围、时间窗、来源 | 用候选程序自身目标替代独立任务目标 |
| TraceIR | tick/phase、外部输入、节点/请求、状态差分、证据及来源 | 只列节点名而丢失反馈身份的执行日志 |
| Report | 每条性质的结论、边界、模型与依赖哈希、重放结果、性能、覆盖缺口 | 一个不区分范围的全局“验证通过”布尔值 |

### 3.1 依赖边界

`core` 不依赖求解器、文件系统或三维引擎。`frontend` 产出规范输入；`model` 和 `properties` 依赖 `core` 与绑定结果；后端只消费 IR；`reduction` 不改原模型；`diagnostics` 使用模型和来源表。CLI 负责文件读写，pipeline 负责连接各阶段。

`benchmark` 的 expected 标签不能传给求解器或性质生成器。模型和性质允许读取同一契约标识，但不得通过 expected 标签或者候选程序的“自称正确”描述生成验证目标。

首期无需一次建齐所有空文件。先落实纵向链路，模块内容增长后按上述职责拆分；测试、研究记录与核心算法分别存放。

## 4. 每一块的具体设计

### 4.1 输入与前端：从文本到可验证的绑定

`loader.py` 以案例根和允许的共享库根解析路径，拒绝越界、循环引用、重复 JSON key、未知版本和非有限数值。所有语义输入生成依赖锁，包含 DSL、绑定、契约、抽象规则、环境、目标、性质、时钟与算法版本。资产哈希仅在附带参考资产时记录为来源信息；缺少 GLB 或节点映射不应触发符号验证的输入错误，资产变化也不应误称为逻辑模型变化。三维标定与动作适配就绪检查归入单独的部署检查。

`legacy_adapter.py` 尽量调用现有 `check_design.py` 的解析/降级能力。首期将通用错误和 T0 特定校验分离；既有 examples 的 IR 和源码映射应通过兼容回归。内部导入旧工具的方式集中在适配层，避免整包散落动态导入。

`binder.py` 构建 `(instance, capability)`、事实提供者、参数、资源、subjects 登记表的索引。名义引用 `material/location/slot/device` 分离，单位严格匹配；能力声明允许的参数与实例参数不混填。原生结构载荷由具名能力适配映射，不能把 JSON 字符串伪装为 Pose。

`scope.py` 采用树上的前向数据流：seq 传播已成功请求集合；par 子分支不可互读未合流的兄弟请求；branch 合流取所有可能分支均可提供的请求；repeat 按激活路径隔离。每个条件使用点校验请求支配，不只检查条件定义位置。

`checks.py` 输出三类独立结果：输入非法、验证模型不支持、部署尚未就绪。仅靠运行路径才能判断的性质留到求解器；静态拒绝不包装成“找到动态反例”。

### 4.2 验证语义补充：将声明变为转换关系

当前 DeviceSpec 与能力适配定义主要提供参数、行为、前置条件和反馈约定，通常不足以完整推出所有中间状态。建议为能力增加独立的 `*.verification.json`，引用原生 spec/behavior 的版本和哈希，先不改现有设备 schema。

每份补充模型需声明：

| 字段 | 作用 |
| --- | --- |
| `capability_ref` | 精确引用能力、适配器及版本 |
| `state_domains` / `initial` | 自有离散状态、初值与允许状态域 |
| `phases` / `transitions` | guard、更新、输出事件、时钟条件及来源 |
| `preconditions` / `hold_conditions` | 执行前与持续条件；说明 controller 读取何种事实 |
| `effects_by_outcome` | 成功、失败、停止和结果未知分别允许的状态变化 |
| `evidence_rules` | 真实抽象状态如何产生观测，延迟和身份如何作用于观测 |
| `read_set` / `write_set` | 含资源、物料、时钟和外部事实的显式依赖 |
| `assumptions` / `abstraction_scope` | 无几何求解、有限物料、有限计时等边界 |

例如机器人搬运至少区分 accepted、approaching、holding、placing、released、committed、stopping。holding 失败允许物料仍归夹具；released 但未提交时不得自动视为交接已完成。输送至少区分 stopped、running、decelerating；停止命令只改变命令状态，环境/设备转换再决定何时实际 stopped。

新增去毛刺、机床、焊接、堆垛能力可先有抽象验证模型，但须标注 `abstract_only`、真实适配未接通。不得通过名称近似把加工动作映射成搬运，或者声称仿真了加工物理。

**应满足的义务与候选实现分开保存。** 契约要求“成功反馈必须同请求”，候选反馈接收规则则描述实际怎样判断。验证器要检查两者关系，不能先将正确性义务硬塞进候选转换，再用它证明自己正确。若模型本就按正确协议构造，该性质是模板一致性检查，不能作为它能检出任意 PLC 实现缺陷的证据。

### 4.3 有限域与状态空间

`domains.py` 根据当前案例选取有限节点、物料、资源、槽位和请求代次。状态向量建议为：

```text
S = (tick, phase,
     node_status, active_iteration, request_state, request_identity,
     feedback_identity, fact_validity, fact_age, provider_epoch,
     drive_mode, held_material, material_holder, support_state,
     reserved_slots, occupied_slots, resource_grants, isolation,
     gate_clock, accept_clock, execute_clock, stop_clock, attention)
```

物料业务 holder 与物理支承不同；不能用单个 holder 枚举的唯一性“证明”实现永不双记账。若待测交接服务用多个本地账本，模型应保留这些局部声明，再验证其一致性；只有强制单一中心账本时，唯一 holder 才是模型结构保证，报告为假设/构造性质。

请求域可约简成 current、prior、other 等等价类别，但必须证明这种约简保留所测错配性质；重复请求和多个在途请求需要额外身份。首版优先有限显式 ID，模型超过范围返回不支持或扩大域，不能让 ID 环绕冒充旧请求。

计时以整数 tick，时长按语言精确向上取整。用于有限完整搜索时，计数器可按最大相关阈值饱和，但必须保留 deadline、age 临界值及超界类，说明等价关系。连续实数的速度/位置先使用有依据的有限谓词抽象，不暗中将任意 REAL 当成整数；未建模数值域明确不支持。

### 4.4 控制器、设备与环境的组合

`node_rules.py` 实现九种节点的状态机，`clock_rules.py` 固定 tick 阶段。逐 tick 可分解为内部微步，但查询须声明观察阶段，不能任意改变“同 tick”的优先级：

1. 冻结上一物理步事实和反馈。
2. 关联已接受请求、处理有效终态证据。
3. 检查持续条件、取消和超时；持续条件故障优先于成功。
4. 形成候选节点集合。
5. 按语言规定排序，原子仲裁并复核 revision/epoch。
6. 提交动作或控制写入。
7. 设备/环境产生下一 tick 的状态和反馈。

后继最早下一 tick 提交，deadline tick 的有效反馈按规范处理；不能为了减少 K 把全部步骤压成同一 tick。初始状态不附带有效 done。

`resource_rules.py` 模型化全资源申请、冲突关系、父作用域授权继承和未知结果隔离。固定仲裁次序属于语义，不是第三章的优化派工。原子申请减少部分持有导致的风险，但不因此宣称系统无饥饿或无一切死锁。

`material_rules.py` 使用事务 ID 去重；预留和占用分开；提交转换明确从“预留”转为“占用”，避免重复提交叠加容量。异常停止保留真实已发生的归属/占用，禁止自动回滚。

`environment_rules.py` 提供具名环境：`nominal_bounded`、`delayed_bounded`、`fault_bounded`。允许哪些迟到/重复/旧请求/断线、何时允许外界移动物料均要显式。外部任意改变状态与不变假设不能混用。持久故障下工艺可能不能完成，关注保守停止与隔离，不强求生产目标最终成立。

`composer.py` 组合规则、明确每一步未写变量保持不变（frame 条件），拒绝未经仲裁的同阶段冲突写。frame 条件对外部可变状态不能误用；否则模型会把设备真实变化“冻住”，得到虚假的安全结论。

### 4.5 性质生成与独立目标

保留 [研究方案](../../docs/method.md) 的 V01–V10：

| 性质 | 典型查询 | 观察点 |
| --- | --- | --- |
| V01 取料互锁 | 进入取料阶段 ⇒ 来源停稳且授权有效 | 取料提交/阶段进入 |
| V02 请求一致 | success ⇒ 同次激活且已接受的 request | 反馈消费 |
| V03 证据有效 | 消费证据 ⇒ 主体/请求/epoch/age 均有效 | 条件及完成判定 |
| V04 资源互斥 | 不存在两个冲突 owner 同时获独占权 | 仲裁后和状态保持阶段 |
| V05 归属一致 | 多方账本/中心 holder 满足声明的一致性关系 | 交接中间及提交后 |
| V06 容量与幂等 | 占用＋预留 ≤ 容量；同事务不重复计数 | 预留/提交 |
| V07 控制退出 | scope success ⇒ exit ack 且 actual stopped | 控制作用域退出 |
| V08 异常隔离 | 结果未知且未确认安全 ⇒ 不虚报清理完成 | stopping、超时 |
| V09 真实目标 | root success ⇒ 独立任务目标及清理成立 | 根成功 |
| V10a 目标可达 | 存在路径达到目标且满足所需终态条件 | 有界存在性 |
| V10b 有界响应 | 接受/触发后 D tick 内应响应或进入允许的处理状态 | 完整时间窗 |

`task_goal.py` 从单独 `task-spec.json` 读取目标，例如 M 属于 C2、位于出口、实际支承成立、两夹具空、两带停稳、无未处置请求。待测程序即使删除 verify 或弱化 final_goal，独立目标也不能跟着删。

`coverage.py` 检查初态非空、触发条件是否可达、性质是否适用。无容量概念的案例不硬造 V06；没有发生 root success 的路径也不能单凭 V09 成立宣称任务正确。合法停机、attention_required 与真正死锁分开：若设备允许继续推进，控制器等待不是死锁。

### 4.6 路径检查与结论分类

定义 `M=(S, Init, T, A)`。安全性在界限 K 内寻找：

```text
Init(s0) ∧ A ∧ ∧[i=0..K-1] T(si, si+1)
         ∧ ∨[i=0..K] ¬safe(si)
```

终态允许 stutter 或逐前缀检查，不能因长度不足 K 丢掉较短反例。环境假设 A 不包括正在证明的 safe。目标可达改成寻找 `goal(si)`，SAT 是目标见证，不能混成违例。

对有界响应 `trigger(t) ⇒ response within D`，仅对具有完整观测窗的触发点求反例：查询到 K 时检查 t≤K−D，另报告尾部未覆盖；也可为触发范围 0..K 继续展开到 K+D。禁止把末尾尚来不及响应判为超时。

`bmc.py` 首期按 tick 增量展开，保留每个 K 和每类性质的任务记录。可以复用前缀公式，但缓存键包括语义、输入和环境，不以文件名或节点数判同一模型。首轮固定相同 K 比较全模型与优化模型，不能一方检查 100 tick、另一方检查 10000 tick 后只比耗时。

| 输出状态 | 严格含义 |
| --- | --- |
| `INVALID_INPUT` | 语法/绑定/结构有确定错误 |
| `UNSUPPORTED_MODEL` | 必需语义或后端支持缺失，未作性质结论 |
| `INCONSISTENT_ASSUMPTIONS` | 初态/环境约束不可满足 |
| `VIOLATED_IN_MODEL` | 有违例轨迹且完整抽象模型重放成立 |
| `NO_VIOLATION_WITHIN_BOUND` | 当前 K 与假设内未找到违例，非全局证明 |
| `GOAL_REACHABLE_WITHIN_BOUND` | 存在达到目标的轨迹 |
| `GOAL_NOT_REACHED_WITHIN_BOUND` | 当前 K 内没有目标轨迹，非全局不可达 |
| `PROVED_ON_FINITE_MODEL` | 显式完整遍历/独立完备证明，附封闭有限模型和完整性依据 |
| `UNKNOWN` / `TIMEOUT` / `RESOURCE_LIMIT` | 未决，不当作安全或准确率正确项 |

每条性质另外记录 `trigger_reachable`、`vacuous`、`applicable`、`incomplete_window`；这些是覆盖信息，不与主求解结论相互替代。全局 ready、部署 ready 单独记录。

### 4.7 显式参考探索与反例重放

`explicit.py` 对小型有限模型用 BFS 遍历，保存 predecessor 和外部输入；到达预算只得到有界/不完整结论。只有状态空间闭合、队列耗尽且时间/身份抽象有依据时，才能报告该有限模型的完整安全性。不能因超过 tick 界限后不再加节点就宣称穷尽。

完整 BFS 可支持有限模型上的状态安全性与可达性结论；一般无界活性还需公平性和循环分析，不在首版证明范围内。有界响应可通过显式义务计时状态检查。终态 stutter 用于保留短路径；非终态没有可推进转换要保留为候选死锁/模型不完整诊断，不能一律添自循环后当作普通等待隐藏。

`witness_decoder.py` 从求解器赋值恢复 TraceIR；`replay.py` 按完整 TransitionIR 逐步重放，检查初态、guard、环境输入、阶段顺序、更新和性质。切片轨迹缺少状态时先求解其全模型补全；不可补全的反例标为抽象伪反例，进入细化，不报真实违例。

共享 TransitionIR 的显式解释器能发现编码错误，但不能独立验证 IR 构造本身。为降低共同错误，另用手写微型状态机、人工审核轨迹、边界表和后续运行日志核对语义。重放通过仅说明反例在声明的抽象模型中成立，不证明物理场景一定能发生。

`explain.py` 输出首个违例点及其因果前缀：例如“bridge 的抓取阶段读取了 arrive_1 旧请求的到达证据；此时 M 已离开出口”。同时给出源码 span、契约 JSON pointer、对象/请求/资源 ID、环境选择及违反的独立性质。路径中最先报警的位置不一定是最初根因，区分两者。

### 4.8 契约驱动优化：研究重点而非首期捷径

先完成 B-FullModel，冻结语义和回归数据，再逐项加入：

1. **依赖切片**：以性质读集合为种子，闭合控制、数据、资源冲突、时钟、事实来源和环境更新；不同设备但共享物料不能判独立。
2. **局部摘要**：只在规定前提下合并不影响性质的内部状态；保留抓取后失败、停止未确认、资源持有及时间信息。摘要前提不满足回退完整模型。
3. **模板/编码复用**：相同契约模板生成规则和共享前缀可缓存；实例参数和 read/write 依赖必须纳入键。
4. **增量验证**：契约变更后重验受影响性质；新资源冲突或新写集合必须重新计算依赖，不能沿用旧闭包。

安全性抽象需要说明路径包含关系；过近似可用于排除违例，但其 SAT 可能伪反例。目标可达的抽象 SAT 同样需要全模型补全；不能把过近似的可达路径当作真实方案。若优化声称对所有查询等价，应论证保持观察与时间语义的关系，并辅以小模型穷举差分实验。差分实验不替代一般正确性证明。

## 5. 核心接口与算法伪代码

拟定接口仅表达职责，不宣称现已有 API：

```python
load_case(path) -> CaseInputs
bind_process(inputs) -> BoundProcess | InputDiagnostics
compose_model(bound, verification_contracts, env) -> TransitionIR
instantiate_properties(bound, task_spec, requests) -> list[PropertyIR]
solve(model, property, bound, budget) -> QueryResult
replay(full_model, witness, property) -> ReplayResult
build_report(results, coverage, dependencies) -> VerificationReport
```

```text
verify(case, config):
  inputs = load_and_lock(case)
  bound = parse_bind_check(inputs)
  if invalid(bound): return input_report(bound)
  coverage = check_model_support(bound, inputs)
  if unsupported(coverage): return unsupported_report(coverage)
  full = compose_controller_plant_environment(bound, inputs)
  if unsatisfiable(full.initial_and_assumptions): return inconsistent_report()
  properties = instantiate(inputs.contracts, inputs.independent_task, inputs.queries)
  for q in properties:
    applicability, trigger = check_coverage(full, q)
    if not applicability: record_not_applicable(q); continue
    model = reduce_if_enabled(full, q)  # 永远保留 full
    result = backend.solve(model, q, q.bound, config.budget)
    if result.has_trace:
      result = complete_and_replay_on_full(result, full, q)
    attach_scope_provenance_metrics(result, trigger)
  return per_property_report()
```

## 6. S04 / T0 的首个纵向实现

从现有 T0 的九个 IR 节点开始：`main`、`load`、`feed_1`、`arrive_1`、`recheck_1`、`bridge`、`feed_2`、`arrive_2`、`verify`。S04 的图片与此前 T0 布局对应，按同一来源家族处理，不重复计独立场景。

先固定单物料 M、R1/R2、C1/C2、被动源 S；验证位置为 source/c1_entry/c1_exit/c2_entry/c2_exit/tool/unknown 等符号区域，不能由画面左右关系推出运输方向。

第一条正常路径：load 抓放并提交交接 → C1 获 writer 并运行 → M 到出口 → 退出控制、确认停稳 → 复查 → R2 抓放并提交 C2 → C2 输送、退出停稳 → 独立目标与清理成立。

至少人工列出这些轨迹再写编码：

| 轨迹 | 预期检查 |
| --- | --- |
| 到达反馈正常，停带延迟但在预算内 | 合法等待，不能误报 V07 |
| arrive_1 旧代次反馈在新请求期间到达 | 应忽略/拒绝；若候选接收规则错误，V02/V03 反例 |
| 减速期间 M 离开出口 | recheck/接收前置条件阻止抓取；删除一个冗余检查未必形成缺陷 |
| 已抓取但停止确认丢失 | 保持隔离，不能虚报物料恢复到源或请求已清理 |
| 候选程序弱化最终检查 | 独立 TaskSpec 继续检查实际目标；保护仍挡住时记录被掩蔽变体 |
| 全过程永不发起动作 | 不得仅凭安全性给出工艺成功；另查目标和触发覆盖 |

优先编写短预算的微型协议夹具验证 deadline 规则；正式 T0 保留既有 60Hz 与 30s/2s/30s/5s 策略，不通过悄悄缩短时间来制造可达或超时结果。完整 T0 的 K 应从阶段响应上界和节点推进开销计算，并记录是否覆盖全程。事件跳步属于后续优化，需保留截止点和事实有效期。

| --- | --- | --- |

## 8. 对比与研究结论边界

沿用 B-Rule、B-FullModel、B-STVerify 和 M-Contract。B-Rule 衡量局部检查覆盖；全模型与优化模型使用相同后端、性质、界限和环境，以分析优化贡献；ST 侧需要同等功能块质量和设备抽象模型，不能与无保护的简单脚本比较。

PLCverif 可作为候选代码侧验证链，其官方流程是将程序及要求转换为后端模型检查输入；它的插件支持范围需要单独做兼容试验，不能预设当前 DSL 能整体直接接入。[PLCverif 官方说明](https://plcverif-oss.gitlab.io/plcverif-docs/userdocs/)

论文应验证的贡献是契约到转换模型/性质的系统构造、可论证的依赖约简、领域反例定位及建模复用成本，而非“使用了 SMT”或“PLC 没有执行前检查”。目前这是一份可实施研究方案，所有性能与检出优势仍待实验。
