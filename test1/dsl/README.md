# 契约驱动的工业工艺 DSL 设计规范

版本：0.1 设计基线。更新日期：2026-10-30。

本文规定 test1 后续工艺领域语言的目标、分层、语义约束、执行协议和验收要求。本文中的“必须”“不得”是本项目拟实施的规则；不表示解析器、编译器、信号管理或运行器已经实现。已有设备建模与受限运行实验的可用范围，以各设备契约及实际执行器声明为准。

DSL 面向工业仿真中的设备能力调用和多设备工艺编排。核心产物是可检查、可执行、可追踪的工艺程序；Lisp 风格文本、图形编辑器和可选 PLC 后端围绕同一工艺中间表示工作。本文不宣称 IEC 完整实现、标准符合性或安全认证。

## 1 开发目标与采用 DSL 的理由

### 1.1 面临的问题

当前需要把“将出口物料送入指定托盘”等业务意图，落实成设备选择、动作参数、条件判断、资源许可、请求反馈和异常处理。直接逐场景编写控制代码时，工艺意图容易与设备编号、信号名、扫描状态、计时及底层驱动混在一起，设备替换和流程调整都会带来重复适配。

已有 DSL 将设备操作映射为动作指令，并通过注册表取得执行参数，降低了动作调用的表达成本。下一步需要解决的重点是：指令能解析不代表工艺能执行，动画结束不代表操作成功；多个合法动作并行时，也可能争用同一设备、物料或交接区域。

本项目因此需要统一表达并检查以下信息：

- 设备提供什么能力，能力需要哪些参数、信号、观测和资源。
- 工艺如何组合能力，分支和并行依赖什么条件。
- 一个请求如何被接受、执行、暂停、终止及确认结果。
- 异构设备替换后，原工艺需要哪些重新绑定与验证。
- 执行结果如何以实际观测和任务条件验收，而不只检查语法。

### 1.2 为什么不直接把 ST 或梯形图作为唯一工艺描述

ST、LD、FBD 等能够实现上述控制逻辑，配合良好功能块库也能形成高层抽象。选择 DSL 的理由是建立一个贴合本项目设备能力和工艺约束的语义层，将共用知识集中到契约、编译器和运行器，减少每份工艺程序对底层细节的重复编码。

| 问题 | 直接编写控制程序时需要处理的内容 | 本项目拟提供的 DSL 能力 |
| --- | --- | --- |
| 工艺意图与控制细节耦合 | 同时处理工序、命令编号、变量及跨周期反馈 | 工艺引用稳定 behavior_id，适配器展开设备协议 |
| 设备异构与替换 | 按设备接口重写绑定和调用逻辑 | 根据能力、类型、单位及协议进行绑定检查 |
| 约束分散 | 条件、容量、资源许可散落在控制代码和说明中 | 契约集中声明，编译与运行阶段按职责检查 |
| 规划结果到执行的语义缺口 | Agent 需同时生成业务顺序和底层实现 | Agent 生成受约束工艺表示，确定性工具完成检查与展开 |
| 执行效果难追踪 | 程序运行正常不直接等于任务达到目标 | 将工艺节点、请求、反馈和任务验收关联 |

以上是设计动机及待验证假设，不是已取得的性能结论。若工程目标仅是固定 PLC 平台上的设备控制，直接使用 ST/LD 和成熟功能块库也是合理方案；DSL 的价值必须通过复用、诊断、修改成本和执行正确性实验体现。

DSL 不承担独立求解全部运动学、物理仿真及最优调度的职责。IK、输送接触与设备驱动由对应执行器负责；资源策略由调度器或明确的基线策略负责；PLC 可作为后续实现目标。

### 1.3 三个研究方向的分工

| 方向 | 输入与输出 | 责任边界 |
| --- | --- | --- |
| 设备契约与工艺编译 | 设备契约＋明确工艺 → 绑定程序及验证义务 | 不从场景自行猜测用户希望执行的工艺 |
| 场景理解与 Agent 规划 | 场景＋用户目标＋能力库 → 候选工艺 | 输出须经过同一契约校验，不直接改设备或物料状态 |
| 运行时调度与派工 | 可执行任务＋动态状态＋资源约束 → 执行选择和授权 | 不绕过动作协议，不代替底层动作求解 |

若最终主要生成自研工艺程序，论文方法名称应相应采用“工艺程序生成/编译与验证”；只有实际实现并验证 PLC 后端时，才以该部分支持 PLC 生成相关结论。

### 2.3 本目录 test.st 的定位

[test.st](test.st) 是 Open-Industry 码垛演示的参考材料：PalletTruck 和 MutingSeq 使用 ST，Palletizer 使用项目自定义的 LADDER 文本。后者可表达梯形图触点、线圈及功能块，但 LADDER/END_LADDER 和字符接线形式不是通用 ST 语法。源项目解释见 [ladder.md](../../../Open-Industry/docs/ladder.md)。

该文件来自原项目 src/editor/demo/demoScenes.ts 的 DEMO_PROGRAM 模板，仍含 `${COURSES}`、`${AGV_PICK_BASE}` 等未展开占位符；2026-10-30 使用原项目 check-st 检查时，在第 287 行报 unexpected character '$'。不能将当前文本当作已展开、可移植或已通过验证的 PLC 基线程序。

该案例说明了语言之外还需设备协议、状态机、互锁和运行配置：Cmd/Exec/Idle 是设备调用约定；Step/OutStep 是工艺状态；Want/Grant 是许可协议，演示调用中 Grant=TRUE，并未进行竞争仲裁。原演示的 MainTask 为 10 ms，场景设备按标签名与控制器绑定；这些依赖不由单个 .st 文件完整承载。

DSL 设计可分析并重建这些关系，但不直接复制其中的设备编号、计时常量和安全相关逻辑。复现基线时须完成模板展开、运行配置与设备绑定，并明确使用源项目规则的部分。

## 3 分层架构与数据职责

```text
场景实例＋设备契约＋明确工艺／Agent 候选计划
                      ↓
DSL 前端解析或工艺图编辑
                      ↓
统一工艺 IR → 类型、引用、能力与约束检查
                      ↓
绑定执行计划＋信号映射＋验证义务＋来源映射
                      ↓
工艺运行器 → 动作网关／设备服务 → 设备执行器
                      ↑                    ↓
               反馈事件与观测快照 ← 物理／感知结果
```

可选 ST 后端从同一 IR 编译受支持子集，使用明确的协议和时钟映射；不要求视图、物料生成等所有指令都能转换为 PLC。

| 对象 | 归属内容 | 不应写入的内容 |
| --- | --- | --- |
| DeviceSpec | 静态能力、参数规则、行为契约、节点与几何结构 | 当前运行任务、临时占用、工艺顺序 |
| SceneDocument | 实例、位姿、参数覆盖、空间连接与具名绑定 | 仿真每步状态 |
| ProcessDocument / IR | 节点、控制依赖、动作参数、条件引用与异常分支 | three.js 对象、求解器、临时句柄 |
| BoundProcess | 解析后的引用、目标协议、版本及执行配置 | 任意修改设备定义的权限 |
| RuntimeSnapshot / EventLog | 观测、有效性、请求、资源、物料归属与执行轨迹 | 反写为设备默认值或作者场景位姿 |

工艺文本与工艺图必须由同一 IR 解析/生成，不维护两份可相互矛盾的权威流程。空间吸附成立，不自动意味着物料可交接、信号已连接或动作已获许可。

## 4 语言与类型基线

- 第一版采用有限的结构化工艺语言，不提供任意脚本 eval、操作系统调用或任意对象方法调用。
- 可以保留 Lisp 风格作为文本前端。最终关键字、词法及完整 EBNF 应在解析器实现前固定；本文的 IR 示例不是旧解释器可直接执行的代码。
- 设备、行为、信号、资源、物料、载位和工艺节点使用稳定 ID；显示名称不可用于猜测式绑定。
- 布尔、有限数值、整数、字符串 ID 及有界集合应有明确类型；位置、姿态等结构参数须声明成员、单位和坐标系。缺少相应结构类型实现时，前端应拒绝而不是隐式转为字符串。
- 有量纲参数显式声明单位，不进行未声明的数值换算。模型默认参数、实例覆盖、本次动作参数与运行实际值分别解析。
- 物料 ID、载位 ID 等引用是不同语义类型；字符串相同不意味着可互换。动态生成对象的引用作用域和存活期必须可检查。
- 条件使用类型化表达式树。首期叶子条件兼容现有设备契约的 `{id,label,source,key,equals}`，组合支持 all/any/not；更复杂比较、计数和几何谓词需另外登记并提供实现。
- 所有算子必须确定边界行为，包括空集合、缺失值、非有限数、除零、越界及整数范围；不支持的情况应诊断，不交给 LLM 猜测或引擎静默修正。
- 源程序、契约、IR 和编译器版本必须可识别；未知版本拒绝执行或经过显式迁移。

## 5 能力绑定与条件契约

### 5.1 调用入口

每个调用至少引用 instance_id、behavior_id 和类型化 arguments。编译阶段解析设备定义版本、executor_ref、所需接口、条件及资源。不存在的实例、不可调用的 passive/observer/internal 行为、未启用能力、缺失执行器或 pending 标定应阻止对应真实执行。

动作、复合行为、持续控制、资源服务及被动对象应分别处理。输送面连续运行不产生全局 done；物料和托盘不因出现在工艺图上就获得自主运动能力。复合行为明确子动作结构与资源归属，不能对外部同一请求重复创建顶层任务。

### 5.2 条件来源与绑定

| 来源 | 定义与绑定要求 | 例子 |
| --- | --- | --- |
| parameter | 引用已解析参数及允许的参数谓词 | 运行模式允许反向 |
| observation | 引用设备/物理/交接服务发布的具名事实 | 出口有料、夹爪为空、目标区域占用 |
| authorization | 引用明确授权提供者及作用范围 | 调度器允许某任务使用交接区 |

逻辑设备信号使用 instance_id/port_id 命名空间，PLC 地址或变量名是可选后端绑定。interfaces 不保存信号绑定；观测键必须在设备 runtime_contract 或明确的场景服务契约登记。

条件必须区分：启动前置条件、执行持续条件、成功完成条件，以及结束后的资源释放判据。不能因为它们都返回 BOOL 就混成一个 ready 字段。

每次读取需带有效性及必要的新鲜度信息。声明默认值、初始 Idle 或尚未加载的传感器值不能冒充有效观测。条件值为满足、不满足、未知三态：not(未知)=未知；all 存在不满足则不满足，全部满足才满足；any 存在满足则满足，全部不满足才不满足，其余为未知。只有满足可通过执行门控；未知需阻止启动或进入已定义的等待/诊断路径。

启动前使用一致快照检查，资源授权和请求提交之间再次核对相关版本与有效条件，防止旧检查结果被当作新状态许可。持续条件失效的响应按动作契约定义，不能所有设备统一硬编码为“立刻回到初始姿态”。

## 6 动作生命周期与请求协议

### 6.1 工艺节点与设备请求分离

工艺节点 ID 描述静态流程位置；每次实际尝试有新的 request_id，并带 run_id、实例、行为与契约版本。循环再次经过同一节点，不复用已经终止的请求身份。外部后端若使用 DINT 索引，映射、溢出和重启后的身份规则必须另行定义。

拟采用的节点状态包括 pending、waiting_conditions、waiting_resources、requesting、running、paused、stopping、succeeded、failed、cancelled。等待条件与等待资源不算执行成功，也不自动归为设备故障。是否已经执行过副作用应在状态或事件中可追踪。

设备动作通过已声明的公共协议或适配器接入。现有 schema.md 的主动离散动作协议仍是请求/接受/反馈的依据，不要求全部持续控制或被动行为具备相同引脚。

### 6.2 必须满足的生命周期规则

1. 请求提交前参数合法、能力有效、必要资源已获准。接受前请求及参数保持稳定，接受后冻结本次执行参数。
2. 同一有效 request_id 重发不能重复执行；不同 run_id 或不同参数不得被误合并。运行器在实际能力范围内提供去重，不能将其解释为真实设备端到端恰好执行一次的保证。
3. 观察到接受后才认为请求生效。accepted、busy、done、error 的保持与清除按设备协议处理，不能由 UI 自行清零。
4. 完成或失败反馈必须关联当前已接受请求；Idle、progress=1 和计时结束不能单独证明成功。
5. 等待接受超时、执行超时与显式失败分别诊断。请求超时但物理结果不明时，进入停止确认或人工处理，不盲目重试。
6. 暂停不释放当前物料与资源。恢复继续同一请求；不支持暂停的执行器必须明确拒绝，而不是重复开始。
7. 停止和取消需等到执行器/设备确认进入契约要求的静止或受控状态。发出 stop 不等于已经停止，失败也不等于资源已空闲。
8. 对同一请求只记录一个权威终态；到达终态后忽略或诊断迟到反馈。结果确认、日志及资源清理必须关联该终态。
9. 故障复位与生产动作分开。复位不隐含重新启动，也不自动把物料恢复到原位。
10. 运行完成与“恢复预览基线”分开；后者是显式仿真/预览操作，不属于生产动作正常成功路径。

## 7 工艺组合与运行时语义

### 7.1 首期支持的组合

| 结构 | 必须规定的语义 |
| --- | --- |
| 顺序 seq | 前一子节点成功后才激活下一子节点；失败或取消不得当成成功跳过 |
| 并行 par | 激活多个分支；资源和条件仍分别门控；所有分支成功才成功 |
| 条件分支 branch | 使用同一快照选择；多条件同时成立需明确优先级，或声明互斥并校验 |
| 有限重复 repeat | 次数为有界非负整数；0 次不产生动作并按组合规则完成；每次调用产生新请求 |
| 条件等待 await | 等待类型化条件满足；区分不满足与未知；声明超时及异常去向 |
| 延迟 delay | 按仿真时间等待；不替代设备完成反馈；0 延迟也不能产生无限同刻循环 |
| 持续控制作用域 | 通过唯一写入者设置启用/设定值，并明确进入、退出及退出确认规则 |

par 首期采用等待全部成功的汇合语义。一个分支失败时停止发起新动作，向其余活动分支提交取消请求；待相关动作停止确认后确定父节点终态。已经完成的物料搬运不自动回滚，补偿必须是显式动作。若后续加入 race/any 或其他策略，应作为不同结构定义。

首期不引入无界循环或任意递归。长期运行通过明确的循环任务和停止条件扩展；不能静默继承旧 spawn-loop 中 count=0 表示无限执行的约定。

### 7.2 时间与事件顺序

运行器必须声明 execution_profile，至少包含逻辑步长、时间单位、事件顺序、条件采样策略、同一时刻的推进上限及暂停规则。测试记录该配置，不能只保存 DSL 文本。

建议首期采用固定逻辑步长：读取有效观测快照；归并上一轮反馈；计算节点转换和可申请资源集合；按确定策略仲裁；复核提交条件并发送请求；设备/物理推进后发布下一份观测。所有阶段的实际实现与时序必须一致记录。

同一逻辑步中，刚收到前驱成功的后继节点最早在下一逻辑步提交新请求，以避免遍历顺序导致多级连跳。并行分支顺序由稳定节点 ID 或显式优先级确定，不由对象遍历顺序、渲染帧或 LLM 回复顺序决定。零时长节点亦受推进预算限制。

超时使用仿真时间。全局会话暂停时冻结仿真时间；单个动作暂停是否累计执行超时由动作策略明确。网页隐藏属于 UI 事件，不可偷偷改变无界面实验的时钟规则；实时联机后端需另设执行配置。

### 7.3 反馈与声明效果

effects 描述期望结果或声明的逻辑更新，并不是直接修改物料位置和归属的授权。物理位姿、检测结果和交接提交分别由对应的唯一状态所有者更新。持续输送依据输送面接触机制驱动物料，不能因 transport_to_exit 存在就改为位置插值。

## 8 资源与交接协议

- 资源分为独占资源、计数容量、载位及几何区域许可；类型、容量、拥有者、持有范围和释放条件必须声明。
- 静态声明 resources 不等于运行时已经获得授权。候选动作检查“可申请”，仲裁产生本次授权，提交阶段检查“已获准”；不能将尚未产生的本次 Grant 当作候选动作的循环前提。
- 第一版建议采用确定性 FIFO、稳定顺序及一次性获得所需资源集合，避免先持有一个资源再无序等待另一个。该策略不构成整个系统全局无死锁的证明。
- 资源管理器集中提交许可；各分支不能依据同一“空闲快照”分别认领同一对象。待执行集合中的动作 individually 可行，不等于可以同时授权。
- 预留和真实占用分别计数，提交交接时将对应预留转换为占用，避免双重计数。载位需要身份，不能仅以剩余数量代替目标槽位检查。
- 物料交接包含接收方预留、发送方释放条件、实际离开/进入观测和归属提交。必须防止一件物料同时拥有两个权威持有者；允许明确记录交接中的过渡状态。
- 取消等待节点可以撤销尚未生效的预留；已经持有物料或执行中止结果不明时，必须保留对应占用或隔离标记，直到释放条件确认。
- 调度器可以替换资源选择和任务排序策略，但不得绕过动作条件、容量约束和结果确认。吞吐量优化不改变 DSL 的成功定义。

## 9 编译产物与 IR 示例

编译至少输出绑定执行计划、实例/信号/资源引用表、契约版本依赖、来源映射和验证义务。诊断须定位到源节点、实例、behavior_id 与具体字段，不只返回“执行失败”。修改源程序、设备契约、关键场景绑定或执行配置后，旧验证记录失效。

以下是**拟议的 JSON IR 片段**，用于说明引用职责，既不是完整项目，也不表示现有导入器或运行器已经支持。资源要求与成功判据从设备契约解析；工艺不另抄一份可冲突的定义。

```json
{
  "ir_version": "0.1",
  "process_id": "pick_and_place_example",
  "execution_profile_ref": "fixed_step_v1",
  "scene_revision_ref": "scene-r1",
  "entry": "main",
  "nodes": [
    { "node_id": "main", "kind": "seq", "children": ["wait_pick", "transfer"] },
    {
      "node_id": "wait_pick",
      "kind": "await",
      "condition_ref": "conditions.input_material_ready",
      "timeout_s": 10,
      "on_failure": "stop_process"
    },
    {
      "node_id": "transfer",
      "kind": "invoke",
      "instance_id": "robot_1",
      "behavior_id": "pick_and_place",
      "arguments": {
        "material_id": { "binding_ref": "bindings.current_material" },
        "target_slot_id": { "binding_ref": "bindings.target_slot" }
      },
      "timeout_policy_ref": "policies.transfer_timeout",
      "on_failure": "stop_process"
    }
  ],
  "conditions": {
    "input_material_ready": {
      "id": "input_material_ready",
      "label": "传送带出口有料",
      "source": "observation",
      "key": "conveyor_1/part_ready",
      "equals": true
    }
  }
}
```

bindings、policies、设备依赖及观测提供者应在完整项目中定义；节点 children 引用必须存在。示例 arguments 的名称及类型必须与实际行为 arguments_schema 匹配，否则应拒绝绑定。explicit await 便于表达工艺等待，动作接受时仍重新检查自身全部前置条件，不能认为 await 曾经成功就永久有效。

## 10 实验配置与验证要求

### 10.1 分层检查

| 层次 | 检查对象 | 主要判据 |
| --- | --- | --- |
| 解析和结构 | 文法、类型、引用、版本、图结构 | 合法程序可解析，非法引用可定位，不支持特性明确拒绝 |
| 绑定和静态语义 | 能力、接口、单位、模式及可判定冲突 | 只调用已声明且可绑定的能力；受限分析范围明确 |
| 协议运行 | 接受、执行、重复/迟到反馈、停止与复位 | 不重复接受，不误用旧 done，不把超时当释放确认 |
| 设备与物料闭环 | 实际状态、交接和任务结果 | 到位、物料归属、容量及资源约束满足 |
| 模型分析（按需） | 状态机/Petri 网/验证器模型 | 明确转换语义、环境假设、状态边界和性质范围 |

独立监测器消费运行观测与事件，不直接信任生成器的“任务完成”文本或执行器单一 progress。监测器与运行器可以由同一项目维护，但应分别实现判据，并用故意错误轨迹和故障注入检验监测器能否发现违反；若物理模型允许任意瞬移，监测结果不能据此支持物理可执行性结论。

### 10.2 必测情形

1. 设备、行为、信号或载位缺失；参数类型、范围、单位或契约版本错误。
2. 观测未知、过期或未就绪，设备初始空闲及残留 done 均不能推进错误步骤。
3. 重复请求、接受延迟、反馈丢失/迟到、执行未到位而动画结束。
4. 同一机械臂、工件、载位或交接区被两个并行分支申请。
5. 并行分支失败、停止中、取消准备、暂停恢复及循环重新调用。
6. 接收方容量不足、预留后目标变化、实际交接失败、物料归属不一致。
7. 同一输入和随机种子重放时，事件顺序及结果可复现；修改契约后必须重新绑定和验证。
8. 预览/演示指令不能进入真实工艺验收，运行姿态不反写作者文档。

### 10.3 对比与指标

方法基线优先采用原有 DSL 生成、直接 LLM 生成同一 DSL、普通模板/状态机编译，以及加入完整契约检查与协议生成的方法。固定设备能力、可用库、场景信息和底层执行模型，分别计量离线建模/适配成本与在线生成/执行成本。

论证相对于 PLC 编程的收益时，除底层手写代码外，应加入提供同等设备能力和协议封装的 ST/功能块基线。若只与完全未封装的代码比较，结果主要反映抽象封装的收益，不能单独归因于 DSL 或契约方法。

主要指标包括合法工艺接受率、非法工艺检出率及误拒绝率、任务完成率、契约违反次数、诊断定位准确率、设备替换修改成本、生成与检查耗时。源代码行数和无异常运行比例仅作辅助；不同抽象层次的语言不直接按行数判断方法优劣。有限测试全部通过不等于所有运行情况下正确。

PLC 对照仅针对双方共同支持的子集：固定设备模型、输入场景、反馈协议、扫描/逻辑步长和验收条件，比较任务事件与状态轨迹。先定义时间容差及采样映射，不要求不同执行时钟的每个内部步骤逐点相等。

## 11 旧 DSL 与执行引擎的迁移

- 保留 arm-pick、conv-transport 等旧名字作为显式迁移入口，映射到设备声明的 behavior_id；旧名称、参数和默认行为不能静默改义。
- 旧引擎负责的动作参数和模型节点映射，可迁入 DeviceSpec 及执行器；动作算法不写入工艺语言解析器。
- 旧 seq/par 的完成、失败及取消语义需逐项核对。实现未核实前，不能假定“同时开始”已经等价于本文的并行执行规则。
- view、appearance、visibility 属于表现层。transform、move-from-to、spawn、destroy 属于受控演示/场景服务；工艺执行配置不得用它们绕过设备驱动、物料所有权、接触输送或交接确认。
- 若 spawn 用于模拟真实出料，必须通过明确的物料源服务与容量、身份、生成策略进行绑定；不能任意复制 GLB 后就算生产完成。
- Mock 可以验证界面及协议通路，但结果须标为 mock，不进入真实动作成功率。部分设备实验已接入不代表八类设备或完整 DSL 已接入。
- 信号桥、物理运行器和动作预览适配器应使用显式适配边界。已有单会话 PreviewController 的状态不能直接当作整条工艺的 RuntimeSnapshot。

## 12 实施顺序与完成判据

| 阶段 | 交付与验收 |
| --- | --- |
| P0 范围与语言冻结 | 选定真实可执行设备和小型搬运流程；固定词法、文法、IR、类型和执行配置；区分草稿与可运行样例 |
| P1 静态编译 | 解析、绑定、类型/引用检查及来源诊断；至少能拒绝有代表性的非法工艺 |
| P2 单动作协议 | 接受、完成、暂停/取消、超时与去重；实际反馈决定结果 |
| P3 组合与资源 | 顺序、分支、有限重复及并行；集中仲裁、交接确认、异常传播和轨迹记录 |
| P4 闭环与实验 | 独立判据、故障注入、可复现任务集及消融比较；按实现范围报告结论 |
| P5 可选 PLC 后端 | 编译共同子集并完成协议和轨迹对照；不阻塞 DSL 主线 |

首个真实闭环可以选取“传送带出口到达 → 机械臂抓放 → 托盘载位确认”，前提是所用设备、观测和执行器已标定并可用；缺少的能力必须先完成接入。仅有参数模板或动画占位时，先开展静态编译与协议模拟测试，并清楚标注证据范围。

每个语言特性进入实现前，必须具备：语法/IR 结构、类型规则、状态转换、时间与并发语义、资源/物料写入权、失败与取消规则，以及正常/异常测试案例。后续扩展应先更新相应契约与版本，再实现解析和执行，避免命令名存在而实际语义不明。
