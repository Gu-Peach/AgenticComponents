若连接真实设备，还需要考虑控制周期、通信故障、设备驱动等执行要求；实体 PLC 承担的功能需要逐项落实。因此，你当前最清晰的目标可以表述为：建立面向车间仿真的工艺语言和执行系统，承担工艺编排及设备协调。
从领域模型入手，对你尤其有价值，因为你的对象存在不同的行为性质：

- 机械臂执行抓取、移动、放置，有明确的阶段和结果。
- 输送机可以持续运行，直到工艺要求停止。
- 托盘和载位通常是被动对象，却具有容量与占用约束。
- 物料交接涉及两个设备，需要保持归属一致。
- 并行动作可能争用设备、物料和空间区域。

用 ST 编写“输送、停带、抓取、放置”，然后绑定这些接口，当然可以。但变量绑定只解决了“读写哪个信号”。工艺还需要确定：

- stopped 是当前实际停稳，还是旧值？
- pick_done 属于本次请求，还是上一次动作？
- 抓取之前，谁取得物料和目标载位的使用权？
- 抓取后失败，物料现在归谁持有？
- 停止工艺时，怎样确认设备已停止并处理资源？
  这些规则既可以写进 PLC 功能块，也可以写进你的 DSL 运行器。两条路线都能实现。 DSL 的潜在价值，是把这些共用规则作为语言和运行系统的统一语义，让每份工艺少写一些重复逻辑。

因此，真正应该比较的是下面两种方案：
方案 工艺作者主要需要提供什么
ST＋设备功能块＋接口绑定 调用功能块，编写状态转换、等待、异常处理及必要的协调逻辑
DSL＋设备契约＋运行器 描述能力组合和工艺要求，由运行器落实规定的请求、等待、资源和退出规则

如果 DSL 能进一步做到：根据契约检查组合是否合法、统一管理物料与资源、自动落实请求与停止协议，并把错误定位到工艺步骤，它就有更明确的价值。这些能力需要实现和实验来证明，不能由语法设计本身保证。

## DSL相比PLC的改进：

第一项实际改进：把“设备调用协议”从每份工艺中集中到能力实现里。
普通文本要求维护：

```text
写命令 → 拉高 Exec → 等 Idle 变假
→ 撤销 Exec → 等 Idle 再变真 → 推进工步
```

DSL 可以让作者只调用“抓层”能力，由公共运行器和适配器完成握手、超时、结果关联。复杂性依然存在，但只实现和验证一次。 换一台握手方式不同的机器人，优先修改设备适配，而非所有工艺。

第二项改进：让物料和任务成为程序中的明确对象。
传统PLC主要通过计数、位置检测和设备状态推进流程。领域DSL可以让物料和任务成为程序中的明确对象，进一步明确表达：哪一个任务，要求哪一台设备，把哪一件物料，从哪里送到哪里。

第三项改进：把并发中的资源关系交给公共机制处理。
作者声明资源需求，公共运行系统完成协调，工艺里不再重复实现每一对设备的仲裁。

第四项改进：让异常成为工艺语义的一部分。
test.st 中已经存在一些需要作者仔细理解的差异：

- 搬运车的 Done 不代表已经返回原位。
- Enable=FALSE 限制步骤推进，不等同于设备受控停止。
- 夹持、释放后的定时等待，不等同于物料交接确认。

DSL强制区分：

```text
请求已接受
动作执行中
工艺目标已达到
设备已停止
资源可以释放
```

第五项改进（主要，编译器任务）：利用车间模型，在运行之前发现问题，在运行时解释问题。
你拥有三维场景、DeviceSpec 和工艺 IR，能够建立代码之外的检查入口：

- 调用的设备是否具备该能力，执行器是否已接入。
- 参数类型、单位、坐标系、物料与载位引用是否匹配。
- 并行分支是否存在确定的控制写入冲突。
- 交接两端是否具备所需条件和服务。
- 运行停在哪个工艺节点，正在等哪个条件、资源或设备反馈。
  例如，界面可以显示：
  “订单 A 的物料 M3 等待托盘载位 S2；该载位被任务 B 预留。”

这比查看 Step=20、某个 BOOL 为假更贴近工艺作者的工作。你的事件记录和来源映射已经为这种诊断预留了设计基础。
