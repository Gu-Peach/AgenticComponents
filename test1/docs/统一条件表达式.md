# 统一条件表达式 ac-condition/0.1

本规范是 DeviceSpec 的可选增量扩展，位置为 `runtime_contract.condition_model`。它补充行为条件的机器可读结构，不修改 `interfaces`、`signal_ports`、行为 ID、参数载荷或 DSL 的工艺控制语法。

作者声明的 `execution_mode` 固定为 `declaration_only`，表示文件本身不能授权或证明运行实现。009 的运行准备现在显式选择 expression profile，校验并绑定已注册的细粒度提供者后，由统一解释器执行条件；文件中的 pending 不自动改为 implemented。禁止仅修改声明标记就切换运行语义。当前实现见[实时工步梯形图说明](../../apps/docs/scene-live-ladder.md)。

## 1. 唯一来源与版本

```text
transport_behaviors[].condition_contract / completion_contract
  └─ source + key + equals
       └─ runtime_contract.observation_definitions / authorization_definitions
            └─ expression_ref
                 └─ runtime_contract.condition_model.expressions[key]
                      └─ expr → bindings[binding_id]
```

保留旧条件 `{id,label,source,key,equals}`。`expression_ref` 指向唯一表达式，不在每条行为和每个实例中复制另一份逻辑。表达式计算的是 key 对应的 Boolean 值，外层仍应用 `equals`。`label/description/note` 只供解释，不能解析自然语言中的“并且”“或者”来生成执行逻辑。

`contract_version` 表示基础 DeviceSpec 结构版本，`version` 表示设备行为能力版本；此次均不自动递增。新扩展有独立 `schema_version=ac-condition/0.1`，派生场景包通过源哈希识别数据变化。只改声明结构不代表改变已注册行为实现。未来启用表达式执行，需要显式的运行配置版本、提供者覆盖检查和等价性验收。

不带 `condition_model` 的契约继续走旧路径；已声明扩展却版本未知、引用悬空或类型错误时必须拒绝编译，不可静默忽略。当前场景编译校验入口为 `apps/scripts/lib/condition_model.py`，由 `scene_devices.load_scene_devices` 调用。

## 2. 容器

`condition_model` 只包含以下字段：

| 字段 | 内容 |
| --- | --- |
| `schema_version` | `ac-condition/0.1` |
| `execution_mode` | 当前只允许 `declaration_only` |
| `unknown_policy` | `three_valued_fail_closed` |
| `bindings` | binding ID → 类型化数据源声明 |
| `expressions` | 既有条件 key → `{status, expr, note?}` |

`status=structured` 表示表达式结构已明确，不表示数据源已注册或结果为真。`status=opaque` 的根节点必须是 `opaque`，只能原样委托旧 source/key。未细化条件画成具名条件块，不把宽泛 `signal_refs` 画成猜测的 AND 网络。

两个条件定义字典中的 key 必须唯一，扩展表达式覆盖它们。历史上未被行为引用的观测定义可以保留为 opaque，但不进入工艺图或计入已实现能力。直接的 `source=parameter` 旧条件仍按原参数绑定处理。

## 3. 表达式语法

| 节点 | 字段 | 结果 |
| --- | --- | --- |
| `all` | `args: Expr[]`，非空 | 三值 AND |
| `any` | `args: Expr[]`，非空 | 三值 OR |
| `not` | `arg: Expr` | 三值 NOT |
| `compare` | `operator: eq/ne/lt/le/gt/ge`、`left`、`right` | Boolean 或 unknown |
| `ref` | `binding: string` | 读取具名绑定 |
| `literal` | `value: boolean/finite number/string`、`unit: string` | 类型化常量 |
| `opaque` | `source: observation/authorization`、`key` | 旧提供者结果，仅允许作为 opaque 根节点 |

每个条件根必须返回 Boolean；比较的数值单位必须相同，integer/number 可作数值比较；Boolean/string 只允许 eq/ne。非数值单位为 `1`。不提供隐式单位换算、JavaScript/Python 表达式、eval、任意函数调用、赋值或写端口运算。当前限制每份契约最多 8192 个检查节点、递归深度 32。

示例来自出口交接的间隔条件：

```json
{
  "op": "any",
  "args": [
    {"op": "not", "arg": {"op": "ref", "binding": "release_material.release_history_exists"}},
    {
      "op": "compare", "operator": "ge",
      "left": {"op": "ref", "binding": "release_material.elapsed_since_release_s"},
      "right": {"op": "ref", "binding": "release_material.release_gap_s"}
    }
  ]
}
```

它表达“首次交付，或距上次实际交付已满足间隔”。没有历史时 elapsed 可以 unknown，由另一支路决定；不能伪造一个很大的时间数值使条件通过。

## 4. 类型化绑定

每个绑定都有 `kind / behavior / value_type / unit`。binding ID 以对应 behavior ID 加点号开头，不能在另一个行为中误用含有不同参数上下文的绑定。

| kind | 额外必填字段 | 含义 |
| --- | --- | --- |
| `signal` | `device=self, port, scope, required_quality=good, freshness=signal_definition` | port 必须存在于该设备 signal_ports，类型和单位一致；保留端口原来的方向和唯一写入者 |
| `parameter` | `parameter` | 引用 params_schema 与实例覆盖后的值，不复制默认值 |
| `profile` | `profile, parameter, implementation_status` | 引用具名执行配置，当前为 scene.assembly@1 的 position_tolerance_m 或 speed_tolerance_mps；缺失不可默认为零 |
| `observation` | `provider, description, scope, arguments, sample_keys, max_age_ticks, implementation_status` | 由受信任、带版本的物理/区域/归属/交接观测提供者求值 |
| `authorization` | `provider, scope, arguments, resource_set=compiled_action_footprint, implementation_status` | 本请求对编译所得资源足迹的授权，不是设备物理传感器 |
| `request` | `field=matching_accepted/matching_success, scope, implementation_status` | 调度器请求账本中的匹配回执，不是裸设备 Done 位 |

observation/authorization 的 `provider` 采用带版本标识，例如 `scene.robot_arm.source_pickable@1`。`arguments` 的值只能是 `{from:self}`、`{from:argument,name:...}`、`{from:payload,name:...}`；后两者分别校验行为 arguments_schema 和 payload_templates 中的字段。不能在共享契约里写死 R1、C4、P01 或某个世界坐标。

`sample_keys` 是提供者所需的观测流，`{self}` 由编译器替换成设备实例 ID，不是任意模板求值。具体主体、目标和资源通过 arguments 与场景登记表解析。声明一个 sample key 不会自动产生该观测：运行接入必须先注册生产者并校验字段/身份。阈值比较可直接使用已有设备参数；执行器内部的容差则引用带版本 profile，不新增一套设备默认值。

本轮 observation/authorization 为 `pending_provider_binding`，profile 为 `pending_profile_binding`，request 为 `pending_request_trace_binding`。这些是模板侧的待绑定标记，不能改成 implemented 冒充运行支持；可执行性由本次准备的注册表、签名、数据质量和身份检查决定。当前 S01 已实现的细粒度绑定由 expression profile 解析；其他提供者仍需实际实现与验收。

### 4.1 身份与质量

| scope | 必须匹配的上下文 |
| --- | --- |
| `run` | 当前运行和解析后的设备/数据来源 |
| `run_subject` | 当前运行及所选主体；ID 经登记表归一化，不能把字符串 ID 和 DINT 直接比较 |
| `request` | 当前运行、设备、activationId、requestId |
| `request_subject` | request 的全部字段及当前主体 |

无主体的 move_to_pose/stop_conveying 不能强制绑定不存在的 subject。世界观测流的根样本可能只有 runId；run_subject 要求在选中的物体/回执上核对主体，不能假装根样本具有请求 ID。环境回执目前不携带完整请求身份时，应与独立的本次请求成功证据合取，不能补造身份。

预先检查的物理状态一般使用 run 或 run_subject；不能要求未提交请求已经有 accepted 或同 requestId 的设备反馈。持续与完成证据按 request/request_subject 关联。

unknown、stale、invalid、disconnected、错 run、错主体、错请求或缺提供者均不能作为已满足的触点。三值逻辑为：`not unknown=unknown`；AND 中有 false 则 false，否则有 unknown 则 unknown；OR 中有 true 则 true，否则有 unknown 则 unknown。只有最终结果确定为 true 才放行。未被实际求值的节点另标 not_evaluated，不混同为 false。

## 5. 三个阶段与防循环规则

1. **前置检查**：判断能否成为执行候选。先成立，再原子申请资源，再做 authorization 重检与提交。普通前置不得依赖“自己已经取得资源”。
2. **持续检查**：仅监控该行为要求在执行中保持的条件，并允许按抓取、搬运、释放阶段切换。夹具为空不是抓放全程必须满足的条件。
3. **完成检查**：本次执行器成功回执与实际结束证据共同成立，之后才锁存工步完成、更新协议 Done 并允许后继。不能由 Done 生成自己的完成条件；accepted/result_id 也不能单独证明物理完成。

execute/start_pick/本动作提交后才写入的 release_waiting_material 不能成为自己启动前必须为真的信号。外部持续许可若确有独立写入者，应另行声明外部输入绑定；当前 S01 由网关写入放行命令，在持续阶段读取。

旧的 signal_refs 是宽泛依赖说明；structured 条件的精确依赖以 expr 的 binding 引用为准。opaque 委托只调用旧原生提供者命名空间，不能再次解析自己的 expression_ref 造成递归。

## 6. 与 DSL 和梯形图的关系

DSL 继续使用 seq/par/branch/repeat/invoke/delay 等组织工艺，不重新暴露设备前置 wait_for。seq 是状态转换和时间先后；par 是并发执行；join=all 是同轮各分支完成的 AND；条件 any 才是 OR。没有信号依赖不构成自动并行授权。

静态工步图由 DSL 节点、行为契约和解析后的条件生成；运行图再附加 runId/activationId/requestId/subjectId/iteration。每次 invoke 有自己的逻辑工步块，同设备不同动作或不同循环激活不能共用一个裸 Done。

表达式执行阶段必须让调度器、轨迹记录和梯形图消费同一份编译条件。先实现只读监视，不建立另一套 UI 调度逻辑。未知叶子不涂成“导通”，不能照设备名称推测 PLC 地址。导出可执行 ST/LD 属于后续独立后端，需要完整提供者、资源与扫描语义映射。

## 7. S01 本轮覆盖

S01 九个作者实例复用五份共享契约：C1–C4、R1/R2、F1、Pallet、Workpiece。共享契约加扩展即可传递到对应实例，无需复制到 device 文件或修改其节点和坐标。

已结构化条件：conveyor 的 transport_to_position、transport_to_exit、release_material、stop_conveying 共 16 项；robot_arm 的 pick_and_place、move_to_pose 共 6 项。其余 149 项既有定义保留 opaque，包含未使用行为、被动响应、观测行为及历史辅助定义。F1 的自主生产行为不等同于当前有限供盘环境服务，托盘/物料也不新增自主执行入口。

场景编译会校验全部扩展，并更新 S01 派生包及目录哈希。旧浏览器实例应重新导入新包。原生运行回归只证明本轮添加声明没有破坏现有执行，不证明上述 22 项表达式已经被新解释器执行；A 阶段之后的运行切换与梯形图实施记录见 [009 计划](../../apps/docs/development-plans/009-2026-11-06-condition-expressions-and-live-ladder.md)。
