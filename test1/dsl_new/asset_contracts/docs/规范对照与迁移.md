# 设备规范对照与迁移

规范依据是用户提供的 [schema.md](../../../docs/schema.md)、[设备契约.md](../../../docs/设备契约.md) 和 [参数契约.md](../../../docs/参数契约.md)。reference-manifest.json绑定原文哈希；原文变更需要重新审核，不能静默沿用旧校验结论。

## 发现的问题

此前九份JSON采用自建asset-contract/0.1结构，不能视为项目DeviceSpec。主要差异为：

| 项目 | 原dsl_new定义问题 | 对齐后的处理 |
| --- | --- | --- |
| 顶层结构 | parameters、behaviors、spatial_interfaces另成一套格式 | 八类统一为DeviceSpec/1.1，使用params_schema、transport_behaviors、interfaces等规范字段 |
| 设备类型 | material、pallet、lift_transport等作为自定义类型 | 文件别名保留；device_type分别为workpiece、workpiece_carrier、lift_table |
| 信号 | 名义字符串作为信号值，缺PLC类型、角色和保持语义 | 使用规范port_id/direction/value_type/plc_type/signal_role/retention；物料等业务身份经登记表投影为整数 |
| 参数 | 自创速度/容量/容差名，缺required与mutability | 按参数契约各类JSON范式组织，保留单位、范围、模式和修改时机 |
| 空间接口 | TCP、槽位、支承和工艺区域混入空间接口 | interfaces只描述空间连接；工艺几何归type_specific_contract，未知坐标显式pending |
| 机械臂行为 | transfer_material、move_to_location、pick、place替代规范行为 | 恢复execute_job、pick_and_place、move_to_pose、grip、release等完整行为表；不做静默别名 |
| 升降与转台 | move_to_height、move_to_location、index_to_angle等自定义入口 | 按lift_to_level、rotate_to_station及其保持/恢复行为建模；辅助输送由transfer_module约束 |
| 输送托盘 | index_carriers、transport_carrier_to、advance_pitch被当成已有能力 | 八类标准契约中不再保留这些自定义能力；当前DSL须明确报绑定缺口 |
| 服务和被动对象 | 统一被动化导致仓储/载具服务丢失 | 恢复库位预留、入库/出库交接和载具服务；服务命令不等于实体拥有驱动电机 |
| 条件 | 另一套left/operator/right表达式且来源边界不同 | 使用{id,label,source,key,equals}，来源为parameter/observation/authorization，注册表引用闭合 |
| 加工设备 | 与八类标准资产并列，容易误认为已有规范 | 明确为ExperimentalAssetContract，待后续补充规范，当前不进入标准DeviceSpec准入 |

逐资产的旧行为、新行为和非规范行为清单见 [audit.json](audit.json)。

## 目前定义的成熟度

八类均为通用DeviceSpec 1.1待接入模板。参数来自文档示例，不是硬件实测；asset.model_key为未绑定模板键，实际GLB、节点、TCP、几何、碰撞与观测区域需要实例适配。不能因为文件可导入就认为能够运行。

本轮按原文逐行为约束拆出并登记前置判据，保留完成判据原意。复杂物理条件仍是具名观测/授权提供者的实现义务，标记pending_provider；描述文本不会被eval。阶段性前置条件与持续互锁分别处理，例如抓取后不再要求夹具仍为空。

行为的input_signals/output_signals引用设备级信号，信号为该行为使用的命令或证据来源；输入默认值不能证明物理条件。仓储信号由仓储服务承载，物料和托盘状态由外层观察者投影，不创建虚假的本体运动命令。

原规范没有为所有泛化动作给出完整结构载荷。此类行为明确保留pending_model_specific_payload，而不编造目标位姿、请求数据或把结构对象塞入REAL。机器人1.4的robot-command载荷是可参考的显式适配边界，当前1.1模板不宣称已经获得该运行能力。

升降目标字段采用规范中的高度输入move_to_level；层号映射需要显式适配。转台保留target_station和角度模式angleTag的互斥参数变体，角度信号单位为°；不能把旧DSL中的rad值无说明地传给它。

所有行为为pending_adapter，所有几何/信号提供者需进一步接入。加工扩展仅保留已有实验定义以便后续讨论；它不是已获标准准入的第九类DeviceSpec。

## 对现有DSL的影响

当前十二份声明式脚本采用旧行为名和旧参数，因此需要重新绑定。例：

- R1.transfer_material不在机械臂规范行为表内；不能只改名为pick_and_place便认定载荷与效果等价。
- C1.advance_pitch没有规范依据，额外接口登记表不能授予它合法性。
- 输送运输使用规范实例的subject_id登记表身份，当前脚本的material和speed_mps参数不能直接替代。
- lift_transport别名现在绑定lift_table，只提供规范的升降及可选辅助横移能力，不自动具有通用水平移动到位置的能力。
- 场景中的被动台座不能仅通过关闭一个自建controlled_feeding开关就冒充标准物料源；后续需要显式建模该被动角色或给出适配定义。

本次不通过修改规范去迁就旧脚本。`tools/check_flows.py`现在执行严格DeviceSpec绑定审计，未知行为、旧参数和实验类型均显式报告；退出码2表示需要重新绑定，不是检查器崩溃。解析器仍可以单独生成控制IR。

详细结果见项目根 artifacts/device-spec-alignment/dsl-binding-audit.json。修正后的资产成为后续重写DSL与适配器的依据。

## 检查证据

1. Python校验器检查规范哈希、完整行为表、参数元数据、PLC类型与方向、条件注册、空间接口职责和未知能力。
2. 平台现有normalizeUnifiedDevice对八类定义均导入成功；加工扩展被标准入口拒绝。该验证仅说明声明导入与引用检查，不能证明实际执行。
3. 回归测试故意引入非规范行为、错误类型、悬空条件、错误信号方向、被动物体输入及错误完成声明，检查器应拒绝。

旧自建资产和旧静态检查冻结在legacy/pre-device-spec，当前资产入口不再从该快照加载定义。三份原始规范未修改。

## 现成案例复核后的补充

详见[模型案例复核](现成模型案例复核.md)。通用检查已允许规范内的行为/参数子集，同时仍检查所有引用闭合。机器人execute_job/wait_time不再将信号或步骤字段推定为标量arguments_schema；空表仍须经过模型命令载荷适配，不能当作无参数动作。
