# 三个现成模型的复核与接入边界

本轮只读取用户指定的robot_UR10、Conveyor_aankws和engine_block源目录，以及必要的现有校验代码；没有修改这些模型、GLB或apps实现。

模型档案见 [model-profiles.json](../model-profiles.json)，保存源schema、README、模型文件及机器人载荷校验器的哈希。档案引用实际源定义，不复制一份可独立修改的设备行为。它们是具体实现参考；当前通用模板仍为pending_adapter，不自动继承案例中的implemented标记。

## 复核结果

| 案例 | 契约／定义版本 | 已有实现与边界 |
| --- | --- | --- |
| robot_UR10 | 1.4／0.1.0 | 单机械臂、位置IK和关节PTP、有限任务步骤、虚拟固定约束抓放；PLC任务触发、全场景碰撞和自动避障未接入 |
| Conveyor_aankws | 1.3／0.6.0 | 一台静态接触输送机与一个指定动态物料的场景模板；原统一行为适配器仍为pending_adapter |
| engine_block | 1.3／0.1.0 | 被动动态刚体，盒形碰撞与惯性近似；没有信号、没有自主行为，mass_kg无默认值 |

三个GLB实际哈希均与各自DeviceSpec.asset.sha256一致。通过平台现有normalizeUnifiedDevice导入检查；这些结果不代表重新运行了IK或物理实验。

## 1. 机械臂参数分为两个层次

robot_UR10的arguments_schema为空，结构化参数通过payload_contract_ref=robot-command@1提供。RobotCommand的顶层字段为requestId、instanceId、behaviorId和steps；位姿、关节、物料身份、等待参数等放在各类型步骤中。

因此，空arguments_schema表示该表不承载结构化命令，不能解释为动作没有参数。本轮已从通用模板的execute_job和wait_time中去掉此前擅自推定的commandTag/duration_s标量参数；保留明确的模型载荷绑定要求。commandTag是信号，不等于原生API命令的动作参数。

| 入口层次 | 当前支持的标识 |
| --- | --- |
| RobotCommand.behaviorId | move_joints、move_to_pose、execute_job、pick_and_place、grip、release |
| RobotCommand.steps[].kind | move_joints、move_to_pose、grip、release、wait_time、wait_signal、set_output |
| 单独控制通道 | pause_pick_intake、resume_pick_intake、hold_motion、resume_motion需要相应控制/信号适配 |

wait_time/wait_signal/set_output虽然是设备定义里的实现行为，但当前作为步骤在execute_job中执行；不能直接放进顶层behaviorId。反过来，payload允许move_joints，不代表它自动成为当前DeviceSpec中可供DSL随意invoke的行为ID。

本轮用现有robotCommandSchema核验了五个载荷：合法位姿命令通过；wait_time顶层命令被拒；execute_job内wait_time通过；请求ID=0被拒；grip行为配release步骤被拒。测试只检查命令格式和关系，不验证目标实际可达。

## 2. 输送机的“声明”与“可运行路径”分开

Conveyor_aankws声明了behavior_code、subject_id、execute以及匹配结果等接口，runtime_execution_contract也描述了完整任务网关。但supported_io明确指出，当前场景输入只开放runTag与speedTag；request_id、behavior_code、subject_id、result_id等尚未实现为对应PLC数字接口。

实际到达观察任务通过场景会话API关联requestId/subjectId，不等于通用PLC握手已经接通。不能根据signal_management.status=implemented，就把全部声明信号都当作可用。

到达出口、实际停稳、下游交接是三个不同事实。transport_to_exit的契约完成依据是本次物料的到达观测；不能据此推断所有执行器都会自动停稳，更不能认为已经完成release_material。以后DSL必须根据真实动作/控制范围组织停止和交接。

同一整带驱动不能独立冻结或定位某件载荷。批量托盘分度仍需要额外的真实设备能力及其正式契约，不由这个单输送机案例自动提供。

## 3. 被动物料不必填满所有模板字段

engine_block的signal_ports和transport_behaviors均为空，符合规范允许按实际需求裁剪的规则。其被动运动由物理世界和外部持有关系完成，不需要为了“统一格式”补start/execute或伪造picked等独立硬件信号。

该案例明确选择box碰撞代理，声明物理尺寸和刚体引用，不需要照搬参数范式中所有shape/diameter等可配置项。mass_kg没有默认值；实例必须提供真实质量或明确选定的实验质量。不得把通用模板示例的1kg默认值偷偷合并进具体案例。

据此修正通用校验：行为和参数可以是规范允许的子集，但未知名称、悬空参数引用、缺少所选能力依赖仍然拒绝。当前八类通用模板仍展示完整规范行为清单；这是一种模板选择，不是每个实际模型必须拥有65条行为的要求。

## 接入规则

1. 通用DeviceSpec描述可复用的契约范式；具体模型档案指出真实源定义与执行范围。
2. 使用具体模型时应显式选择它的版本和载荷适配，不将通用模板的缺失字段、默认值或implemented状态自动合并进去。
3. DSL绑定分别检查行为表、调用入口、标量参数、结构载荷、可用控制源和运行能力。仅名称一致不代表可调用。
4. 当前模型档案是只读引用与审计信息，自动实例选型/载荷编译适配仍待实现。当前严格审计仍会拒绝未绑定的模型载荷，不将args={}当成完整调用。
