# 有限批次与协调执行语义

当前源语言采用[ac-python/0.1规范](Python风格DSL规范.md)。下文括号形式用于说明控制IR的原始组织关系；实际场景请编辑process.py。

每个场景定义一批有限任务及其全部完成条件。任务单位可以是工件、装载托盘或入库订单；不会把一次动作完成当成整批完成。单设备动作遵循统一资产契约，场景控制表达批次、等待、并发和资源协调。

## 文件与数量

- `batch.json` 是具体任务清单，含所有物料身份、托盘装载关系、目的地以及工位候选。数量由清单长度确定。
- `process.py` 描述有限循环、并发上界、资源范围和动作。
- `bindings.json` 登记资产实例、逻辑位置、外部来料/出料、初态及执行假设。
- `task-spec.json` 独立保存预期数量、身份和终止条件。改变候选程序不得同步削弱目标。

批次数量不等于同时在线数量。未放行物料在显式外部缓冲区登记；外部到料提供者必须确认入口和所属设备的容量含预留仍可用，才可以实际送入。`await` 只观察，不生成物料或写位置。

`pallet_count` 指本批明确流转或换盘的任务载具数量，不包括固定的接收托盘。S01有三个载料托盘、每盘四件，S02有六个流转托盘，S10有三个依次换入的托盘。

## 控制节点

```text
(process "ac-flow/0.2" Sxx
  (sequence ... (verify batch_goal)))

(for-each jobs job body)
(parallel-for jobs job 2 body)
(with-resources (R1 C1) body)
(await input_present $job.material $job.input 1800 tick)
(invoke op_id R1 transfer_material
  (arg material $job.material)
  (arg source $job.input)
  (arg target $job.target))
```

`sequence` 等前一节点确认完成后推进。`for-each` 按清单顺序逐项执行；`parallel-for` 同时最多开放指定数量的任务，结束一个后才补入后续任务，最终汇合全部清单。变量采用词法作用域，`$job.material` 解析当前记录字段；禁止隐式选择下一件物料。只有显式有限清单可被遍历。

同一个模板 invoke 可在多次循环中执行，但运行身份必须包含 run_id、scene_id、任务ID、循环路径和模板步骤ID。请求编号在本次运行中唯一，禁止复用上一轮的完成反馈。模板本身的步骤ID须唯一。

`with-resources` 对列出的实例操作资源实施互斥；集合原子申请，不能部分获得后等待其余资源。嵌套块保留外层所有权，同任务重入已持有资源不重复申请。运行器需要公平排队，并在期限内报告阻塞；本语法不保证所有可能调度均无死锁。

资源范围结束仅释放临时操作许可，不清除真实物料占用。每次转移的源/目标、装夹、容量预留必须由契约服务在动作提交时复核。`target_available` 只是等待提示，不能在它通过后跳过原子预留。某工件占用C1时，另一工件不能因C1操作锁已释放就挤入容量为1的输送机。

动作仍是 request_v1 下的离散调用，等待匹配的接受、完成与业务证据。`transport_to_exit` 自身负责到位后停稳。连续 run 不由普通 invoke 调用。故障、等待期限或总期限到达时，停止接纳新任务，取消相关活动分支，等待停止确认或进入 attention_required；不能继续把整批计为成功。

## 等待谓词

| 方法 | 参数 | 等待什么 |
| --- | --- | --- |
| `wait.input_present` | material, location | 指定物料实际到达入口或取料位置，身份和支承有效 |
| `wait.target_available` | location | 目标位置当前可接收；动作提交时仍需原子预留 |
| `wait.output_available` | device | 出料设备当前具有接收容量和可用状态 |
| `wait.output_departed` | material, device | 指定物料已在对应出口完成交接并被下游移走 |
| `wait.empty_pallet_present` | pallet | 指定空托盘已换入码垛工作位并停稳 |
| `wait.full_pallet_departed` | pallet | 指定托盘已按清单装满且由外部换盘方移走 |
| `wait.carrier_present` | pallet, location | 指定载料托盘实际到达主线入口或指定位置；不要求托盘为空 |
| `wait.carrier_empty` | pallet | 指定托盘没有剩余实际物料或未提交交接 |
| `wait.carrier_departed` | pallet | 指定空托盘已到达主线末端并被外部接盘方移走 |

这些事件必须有有效性、采样时刻、代次和主体身份。不能用定时等待后自动置真。每个await有单次期限，bindings.execution.deadline_ticks还有整批总期限。

## S02：整线停带与并行拆垛

```text
(dispatch-waves pallets cells
  (line C1 index_carriers)
  (policy fifo-first-reachable-idle)
  (bind pallet cell)
  station_body)
```

此节点是明确的协调控制语义，不是已经实现的运行器调用。它的每一波必须依次完成：

1. 从待处理托盘FIFO队列取候选，选择沿线可达、空闲、输出可接收且满足同一主线运动计划的工位。每个工位至多一个托盘，每个托盘绑定一个工位。无可行分配则等待，不把托盘从待处理集合删除。
2. 生成具唯一 transport_plan_ref 的入站计划：列出全部在线托盘及新增托盘、当前位置、目标工位、实际载荷和顺序。队列里尚未入站的托盘不能被遗漏计入已处理。
3. 申请主线独占运行权限，确认所有机械臂退出运动区，再调用 C1.index_carriers。单驱动计划必须保持运动兼容、间距和先后次序，无超车；无法由共同驱动完成则拒绝计划或缩小波次。
4. 核对每个托盘实际到站及整线停稳。主线在拆垛波次中保持禁止运动；将各托盘工位的交接子权限授予对应worker，而不是允许worker重新启动主线。
5. 对波内各 `(pallet, cell)` 并行运行 station_body；每个worker顺序遍历本盘全部items。机械臂把物料送到该cell的出料线，退位，出料线输送并由下游确认移走，才处理下一件。
6. 所有worker成功汇合，独立核对每盘实际剩余库存为零、没有活跃请求且机械臂全部退位。
7. 生成并执行整线出站计划，把这些空托盘送至主线末端。外部空盘接收者确认出线并腾出容量，再处理下一波。

六盘、三工位且全部可用时，名义计划是两波各三盘；如果只有一或两工位可用，可采用较小波次。工位选择是固定规则，未研究最优调度。每波均冻结分配；执行中出现故障不把已执行一半的托盘无证据地重派给其他工位。

这一方案允许三台机械臂同时拆垛，但拆垛时整条主线不移动。不同工位独立输送的方案需要额外的分区驱动模型，当前没有暗中假设该能力。

托盘输送使用新增 conveyor 0.2.0 的 index_carriers 行为。输送对象包括载具及盘上物料，盘上物料的局部槽位关系保持，世界位姿由实际运输更新。计划ID只是注册表引用；运行器必须提供有类型的运动计划记录及独立几何/间距检查，不能凭字符串ID推断可行。

## 各场景控制选择

- S01：载料托盘依次停靠两个分类取料工位，A类送C2、B类送C3，清空后出线；采用整线共驱一次一盘。
- S03、S04：最多两件在途，前后段按容量与设备锁形成流水。
- S02：有限托盘队列、动态空闲工位选择、整线输送屏障、波内并行拆垛。
- S05：共用一条进出料输送带，按有限批次逐件完成，防止未经建模的回流竞争。
- S06：前段进料和后段出料可重叠；转台的上料—转位—下料—复位周期互斥。
- S07：先四件分层入库，通过 inventory_stored 检查点，再按订单逐件出库。
- S08：单加工工位串行，但下一件进料准备可与当前加工或出料重叠。
- S09：两台机器处理不同工件；R1的上下料和退位通过同一资源互斥。
- S10：三盘各四件，逐盘码满并等待真实换盘确认。
- S11：共用装卸台和转位台，有限逐件循环。
- S12：两侧工位加工不同工件，转台交接互斥；最多两件在途。

## 独立整批验收

验收比较完整ID清单，不仅比较计数器。每件物料需要对应目标出口/载位的真实交接记录，且不能重复交付；加工任务需要本次运行的工件/工位/配方记录。出料后物料可在外部收集区，因此目标使用有效交接历史，不要求全部工件同时堆在一个出口。

S02必须有24件物料到对应分配工位出料线的记录，以及6个空托盘到达末端并出线的记录；不是要求6盘同时停在末端。S10必须有三盘与每盘四件清单匹配的装载和离开记录。S07必须先有每件在指定库位的入库证据，再有出库交接证据。

全部场景还要求无待分配任务、无未终结请求、工具为空、驱动停止及临时操作许可清理。实际物料占用不因任务结束被清空。

## 检查与实现边界

```powershell
python -B tools/check_flows.py
python -B -m unittest discover -s tests -p "test_*.py"
python -B asset_contracts/tools/validate_contracts.py
python -B -m unittest discover -s asset_contracts/tests -p "test_*.py"
```

检查器解析新语法，展开有限绑定，校验ID、类型、单位、资源范围、能力及任务数量。S02会检查每个托盘绑定到每个候选工位的参数与动作意图，而非只检查预选的R1路径。

顺序意图摘要只验证工件源位置、加工装夹、退位和目标覆盖等显式矛盾，假定单动作履行契约；并发任务采用代表性串行顺序展开。它不执行真实调度、不分析所有交错、不证明无死锁或物理可达，也不模拟托盘运动计划。`binding_checks`是检查次数，不是实际动作执行次数。

并发/波次运行器、运动计划注册、资源/容量服务及实际设备适配尚未接入。所有静态结果保留 `runtime_ready=false`。当前Python前端将这些控制语义编译为统一IR，旧Lisp仅供迁移回归。

S01增加carrier_present(pallet, location)、carrier_empty(pallet)、carrier_departed(pallet)三项带期限等待；提供者和判据见[S01说明](processes/S01/README.md)。

## S01数据职责

S01批次只包含托盘和物料库存，不包含工序或运输计划。到站、类别处理、出线等顺序由process.py显式组成；现场物理位置与可达关系保存在bindings，底层运动计划由契约执行层按当前状态派生。
