# 契约驱动的声明式协作 DSL

语言标识：`ac-declarative/0.1`。本规范定义新的语言目标与语义；示例为design_only，现有ac-python/0.1前端尚不支持本版本。本文不把已有静态测试视为新语言的实现验收。

## 1. 语言目标与设计修正

DSL的任务是显式描述设备如何协作：哪些动作依次发生，哪些分支可以并行，满足什么条件才能推进，重复处理哪些对象，何时等待或停止。设备动作的具体协议、信号绑定、前置条件和完成依据来自设备契约。

上一版以async函数、场景专用worker和dispatch函数为主要组织方式，弱化了统一控制模型。本版恢复旧dsl/01-language.md中的九种控制节点；Lisp、Python风格及图形界面都是同一控制图的表达方式。不同场景的数据与控制图不同，控制算子及解释规则相同。

Python风格不要求用户定义async def或控制器函数。`with par(...)`表示声明并行节点，`invoke(...)`表示声明契约调用节点。它们表面类似Python调用/上下文管理器，但只由DSL前端解析成节点，不执行Python代码，也不直接调度动作。

结构嵌套用来表达控制图的父子关系，例如repeat内部有par，par分支内部有seq；它不依赖每个场景自行实现调度函数。

## 2. 五类信息的边界

| 信息 | 内容 | 不承担的职责 |
| --- | --- | --- |
| 设备契约 | 能力、参数、条件、效果、命令/反馈、连续控制协议 | 规定某个场景完整工艺顺序 |
| 场景绑定 | 设备身份、信号适配、物理位置、可达/冲突关系、事实提供者 | 保存“第一步、第二步”的控制程序 |
| 生产任务batch | 有限物料/托盘清单、类别、装载关系、订单要求 | 保存行为名、逐步到站路线和执行脚本 |
| ProcessIR及DSL | 九类控制节点、条件树、对象引用及控制依赖 | 自行伪造设备完成反馈 |
| 运行态与事件记录 | 当前激活、请求、位置/归属、资源、信号证据和进度 | 反写为静态契约或修改独立目标 |

task-spec保留独立验收要求。订单可以规定最终交付目的地与加工要求，DSL决定如何组织动作完成要求；订单要求不等于每一个动作的预编排。

## 3. 唯一核心：九类控制节点

| 语义节点 | Python风格声明 | 语义 |
| --- | --- | --- |
| seq | `with seq("id"):` | 子节点按顺序推进；一个成功后启动下一个 |
| par | `with par("id", join="all"):` | 同时激活所有分支候选，等待全部成功后汇合 |
| branch | `with branch("id", mode="exclusive", timeout=seconds(30)):` | 用同一快照选择一个case，选择后不切换 |
| repeat | `with repeat("id", count=N):` 或 `with repeat("id", over=items, bind="item", limit=N):` | 有界重复同一控制子树，逐轮重新建立激活和请求身份 |
| invoke | `invoke("id", R1, "transfer_material", ...)` | 引用契约中的离散动作、复合行为或服务，等待契约结果 |
| await | `wait_for("id", condition, timeout=seconds(30))` | 条件为真才完成，假或未知继续等待至期限 |
| delay | `delay("id", seconds(1))` | 经过指定仿真时间后完成，不证明设备动作完成 |
| with-control | `with with_control("id", C1, control="drive", ...):` | 持有持续控制写入权，进入确认后运行子树，所有退出路径均执行受控退出 |
| fail | `fail("id", "E_CODE")` | 显式产生业务失败，触发相应停止/清理 |

process是文档外壳；case和otherwise是branch的结构字段，不是新增运行节点。条件表达式、类型引用、集合选择和单位构造也不是设备动作。

九种节点均为必需的语义定义；当前实现覆盖情况必须逐项记录，不能只支持seq后仍声称完整支持本规范。

## 4. 声明式Python表面语法

```python
with process("example", version="ac-declarative/0.1"):
    with seq("root"):
        wait_for("ready", fact("input_ready", material=task.material), timeout=seconds(30))
        with par("two_independent_operations", join="all"):
            invoke("left_action", LeftDevice, "operation", material=task.left_material)
            invoke("right_action", RightDevice, "operation", material=task.right_material)
        delay("settle_observation", milliseconds(100))
```

这是语法说明，设备与operation必须在实际绑定中存在才能准入。正常工艺脚本不出现async def、asyncio、yield、资源请求实现、临时回调、任意for/while或Python if。

允许的AST结构为固定with声明块和固定叶节点调用，参数限常量、受控引用及类型化表达式。没有导入、赋值、类、用户函数、lambda、推导式、反射、eval和任意对象方法调用。

原生Python的for、if不承担控制语义：循环使用repeat，分支使用branch。名称为await的Python关键字不适合作普通函数名，因此Python前端用wait_for，生成的IR节点仍为await。

块内相邻节点并不一概顺序执行：直接子节点的关系由父节点决定。seq中的子节点顺序推进，par中的子节点并行候选。任何不明确父组织关系的节点集合均拒绝，避免靠解释器执行源码的先后次序决定工艺。

## 5. 节点语义及边界

### seq与par

seq至少一个子节点。par至少两个分支，首版join固定all；不提供隐含的first-success或竞速语义。分支内部需要多个步骤时显式包seq。

par表示允许并发，不意味着绕过互锁。只有互不冲突的请求才可同时获得许可。两个动作争同一可排队资源可以等待；两个持续控制节点争同一输入写入权属于绑定冲突。

一个par分支失败后，停止新的生产提交，取消已激活兄弟分支，等待停止和必要清理。已发生的物料交接不回滚。停止未知时进入attention_required，不为了让par返回而伪造取消完成。

### branch

branch含一个或多个case以及唯一otherwise，并有正的选择期限。

- exclusive：所有条件已知且恰好一个为真才选中；多个真报分支冲突；存在未知则等待；全部假才走otherwise。
- ordered：按源顺序选第一个真；更早条件为未知时等待；全部假才走otherwise。

```python
with branch("quality_route", mode="exclusive", timeout=seconds(30)):
    with case(eq(fact("quality", material=item.material), "accepted")):
        invoke("send_good", Robot, "transfer_material", material=item.material,
               source=Inspection.work, target=Good.entry)
    with case(eq(fact("quality", material=item.material), "rejected")):
        invoke("send_reject", Robot, "transfer_material", material=item.material,
               source=Inspection.work, target=Reject.entry)
    with otherwise():
        fail("unknown_quality_code", "E_QUALITY_VALUE")
```

otherwise不吞掉未知观测；选中分支失败也不会再尝试另一个分支。

### repeat与有限数据选择

batch.pallet_count/item_count/max_items_per_pallet等统计字段由冻结清单派生，并与清单一致，不由另一份步骤计划填写。

count是绑定期可确定的非负整数，最大10000。可允许batch中的整数计数与整数字面量的有界加减，在绑定期求值并检查范围，不提供任意Python算术。count=0是明确的空循环。

over绑定有限集合，激活时冻结成员、顺序、身份及提供者快照；limit给出最大基数。参数集合来自batch或已登记的场景库存服务。集合可以已知为空，不能把未知集合当空集合。集合变化不会使当前轮次跳到另一个物料；变化冲突应重新等待或失败，而不是静默替换身份。

`items_at(station, category="A")`只是一种待登记的只读集合表达式：读取当前停靠载具的库存。它不选择机械臂、不生成动作、不改变物料，也不携带工艺路线。必须检查站点快照、载具身份、类别、库存上限和数据有效性。

每次repeat激活具有独立iteration_path。par内两个不同repeat的变量作用域分离，不能访问兄弟分支的临时绑定。运行器在每轮使用新请求身份，不沿用上一盘的Done。

### await、delay与fail

await只读条件，不保留操作许可。条件为T通过，F/U等待；到期区分“条件为假”和“证据未知”。delay使用仿真时间，不作为运动或交接的成功判据。fail只产生业务失败，不直接修改设备状态。

### invoke与with-control

invoke绑定到instance＋behavior。编译器从契约导入参数类型、执行器、前置/持续条件、命令绑定、反馈关联、完成证据、资源和停止策略。工艺只提供对象和参数，不复制协议。

continuous行为不能伪装成一次性invoke。with-control必须绑定已登记的控制配置：唯一writer、进入设定及确认、持续条件、退出设定、实际停止证据和可释放规则。它不是普通资源锁；父节点失败或取消也必须执行退出协议。

```python
with with_control("feed_window", Conveyor, control="forward_drive",
                  setpoints={"speed": quantity(0.2, "m/s")}):
    wait_for("part_arrives", fact("material_at_exit", material=task.material),
             timeout=seconds(30))
```

本例需要对应控制配置已声明并实现，不能直接把它映射为当前run行为而省掉进入/退出证据。

## 6. 条件、资源与信号如何来自契约

条件统一为类型化IR：fact/ref、eq/ne/比较、all_of/any_of/not_。各事实须有提供者、类型、单位、主体/请求限定和有效期。F与U不同：缺失、过期、错主体、错代次均是U，默认值不能充当成功观测。

工艺显式等待跨动作依赖，例如某托盘到站、前工序完成、外部许可或出料接收。单行为固有的夹具为空、载荷限制、当前请求关联等条件由契约自动引入，不要求作者手写重复检查。

资源与写入冲突由契约声明和场景绑定共同导出。取消原版脚本中到处手写resources(R1,C1,C2)作为主要语义的做法；编译器应能从行为及参数推导当前涉及的设备、物料、位置和容量需求。缺少资源声明时报告绑定阻塞，不能默认无冲突。

par内竞争资源通过集中仲裁处理，只有完整授权后才能提交。授权是仲裁结果，不应同时被要求作为申请授权前必须已真的条件，避免自锁。with-control可把兼容子能力声明的授权委托给子动作；未声明委托则拒绝隐含继承。

命令与实际反馈分别记录。以机械臂搬运为例：

```text
invoke(R1, transfer_material, M, source, target)
  → 解析R1契约与实例信号映射
  → 检查参数、前置条件、物料/目标容量及授权
  → 分配请求身份，写参数及Execute
  → 确认Accepted及身份，保持/撤销请求握手
  → 监控持续条件，等待本次结果及放置/释放证据
  → 记录交接、清理临时许可，节点成功
```

成功必须来自关联证据，不从声明的expected_effects直接写出。失败保留已经发生的物理事实。

## 7. S01真正的并行协作

目标并行为：R1处理当前进入第一工位的托盘A类时，R2同时处理前一托盘的B类。不是在一个托盘的串行程序外随意放一个parallel_for。

共同驱动可以采用共同分度，前提是托盘节距、工位间距、入口/出口容量和停止控制支持每拍统一移动。示例采用以下明确的设计假设，尚未从GLB验证：

1. 工位1到工位2以及工位2到出线点的有效分度关系已标定，能由同一次主线推进实现。
2. 主线容量必须覆盖两个停靠托盘及声明的进出线过渡占用，不能沿用当前S01容量为1的绑定。停带时两个工位可分别保持一个托盘，机械臂运动区不冲突；两条绿色出料线独立。
3. 主线移动前，两个机械臂均完成当前分支并退位，全部出料/夹持相关交接已确认。
4. 入口按冻结队列最多补一盘；出口接盘者确认移走，避免末端堵塞。盘上剩余物料保持实际支承。

```text
拍1停稳：R1处理P01的A类；R2工位为空
拍2停稳：R1处理P02的A类 ║ R2处理P01的B类
拍3停稳：R1处理P03的A类 ║ R2处理P02的B类；P01空盘出线
拍4停稳：R1工位为空     ║ R2处理P03的B类；P02空盘出线
拍5结束：P03空盘出线，整批验收
```

每拍结构为主线推进并确认停稳 → par(R1分支,R2分支) → 全部分支完成/退位 → 下一拍。共享主线在取料时保持停止，但两台机械臂确实可同时处理不同托盘。

N盘的两工位无故障参考流程最多N+2次推进，用于填充与排空；这个数不是可以忽略到位/出线证据的定时推进次数。堵塞或未知反馈时等待，超时进入失败清理。独立验收要求所有物料和托盘ID完整覆盖。

如果物理主线不满足共同分度条件，应选择明确的独立分区适配或重新设计站位；不能把不支持的并发写进实验后假装执行成功。

完整声明式示例见 [S01共同分度示例](examples/S01.pydsl)。它显式包含par，但依赖尚未实现的共同分度能力和库存快照提供者，见 [示例接入条件](examples/requirements.json)。现有processes/S01/process.py继续作为旧串行原型，不代表本规范的最终S01实现。

## 8. 中间表示与三种前端

所有前端生成同一控制IR，至少含：版本、入口、九类节点、条件树、类型化参数、节点ID、源映射和环境引用。节点没有源代码函数指针或Python闭包。

Lisp的 `(par (seq ...) (seq ...))` 与Python的 `with par: with seq: ...` 以及图形编辑器的并行框具有同一语义。语法表面不同不改变请求、时钟、仲裁或失败规则。

case/otherwise降级为branch的cases/otherwise字段；repeat的count或over具有互斥配置；with-control的control_ref指向版本化控制配置。每个节点除入口外只有一个结构父节点，不允许多个父节点共享可变激活状态。复用通过已登记的声明式控制子图在编译期实例化，不使用场景专用Python函数执行控制。

首版不必开放用户自定义子图宏。固定九种节点和可复用设备契约本身就是统一规范；共同工艺模式以后可加入有类型参数的声明式库，展开后仍只有九类运行节点。

## 9. 时钟、编译与后端

沿用旧语言的固定逻辑时钟设计：先读取一致反馈快照，归并终态证据，处理持续条件/取消/超时，再计算候选、仲裁、提交命令，最后推进设备与物理并发布下一快照。后继最早下一tick提交，不依赖源码函数执行速度。

deadline同tick内先核查有效完成证据，再判相应超时；持续条件失效优先于成功。仿真暂停冻结逻辑时钟；真实设备接入须另有时钟配置。默认60Hz，时间有理换算为整数tick并向上取整。

编译阶段：

1. 声明式语法/AST白名单检查，生成控制IR。
2. 控制树、作用域、集合上限、条件及参数类型检查。
3. 实例和行为契约绑定，导入前置/持续/完成/停止协议及资源足迹。
4. 构造请求身份、并发依赖、互锁、单writer和交接义务。
5. 形成BoundProcess及依赖锁；缺设备能力、观测、控制配置或几何前提时保留明确blocker。
6. 场景后端解释BoundProcess；可选PLC后端从相同IR生成支持子集的扫描状态、请求握手、定时器、互锁及反馈判断。

Python方法或类可以用来实现编译器和后端，但不是工艺作者必须填写的控制程序。SimPy可承载事件与仿真时间；它不会自动提供工业请求协议、原子授权或停止隔离。PLC输出则须另外验证扫描阶段和事件投影，不因共享IR自动获得等价证明。

## 10. 实施与验收边界

本次交付是重新设计的规范和设计示例，不将ac-python/0.1的现有解析器改名冒充新语义。现有十二份脚本仍是旧原型；后续应按以下依赖迁移：

- 先实现九节点统一IR与两种声明式前端；逐节点检查正常、未知、失败和取消边界。
- 实现契约绑定、条件/集合快照、资源仲裁、持续控制退出与并发汇合。
- 接入S01共同分度能力，验证两机械臂处理不同托盘存在实际时间重叠，同时主线移动与抓取不冲突。
- 再迁移十二场景，按真实工艺选择seq/par/branch/repeat；不要求每个场景都用全部算子。

最小验收包括：并行分支同时激活且遵守互锁；空/未知工位分开；分支不吞未知；循环不复用请求；delay不证明成功；with-control在失败路径仍退出；缺契约依赖拒绝；批次数量与独立目标完整；新旧前端生成等价控制IR。

图能解析、规范示例通过Python AST解析，只证明表面结构可表达，不证明并发执行、运动可行或信号逻辑已经实现。
