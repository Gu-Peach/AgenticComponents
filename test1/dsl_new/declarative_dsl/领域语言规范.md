# 契约驱动的声明式协作 DSL

当前版本为`ac-declarative/0.3`，十二场景均采用此版本。工艺只声明设备行为及其顺序、并行、分支和循环；设备行为的前置条件、持续条件、结束判据由编译绑定层从契约导入，运行时根据信号和观测证据求值。当前只实现静态绑定检查，尚未实现运行调度。

0.3不提供`wait_for`语法，也不要求作者在动作前后手写就绪、到位或完成判断。0.1/0.2仅为历史程序保留解析能力；S02—S12也已迁移声明，运行适配仍待实现。

## 1. 信息职责

| 信息 | 职责 |
| --- | --- |
| 设备契约 | 唯一行为ID、标量参数、可调度性、前置/持续/完成条件、命令与反馈端口 |
| 实例绑定 | 模型身份、位置和标定、单动作载荷编码、信号与条件提供者、有限对象登记 |
| batch | 有限生产清单、类别、初始装载、由清单派生的数量；不存逐步路线或执行程序 |
| DSL | 设备行为之间的控制关系、动作对象和目标 |
| task-spec | 独立批次验收要求，不能为使流程通过而改变 |

绑定允许描述条件与信号的对应关系，不能藏入工序序列、循环或选机程序。无法自动推出的空间与交接条件必须在设备契约/实例条件绑定中明确提供；编译器不能凭行为名猜测。

## 2. 八类控制节点

| 表达 | 含义 |
| --- | --- |
| `with seq("id"):` | 子节点依次执行；前一节点按契约成功后才进入下一节点 |
| `with par("id", join="all"):` | 至少两条分支并行候选，全部完成才汇合 |
| `with branch("id", mode="exclusive", timeout=seconds(30)):` | 按业务条件选择case，另支持ordered模式；设备前后置条件不用branch重写 |
| `with repeat("id", count=N):` | 有界重复子树 |
| `with repeat("id", over=集合, bind="item", limit=N):` | 自动核查集合有效性，冻结快照后逐项处理 |
| `invoke("id", R1, "pick_and_place", ...)` | 调用契约中的有限行为并由契约判断结束 |
| `delay("id", seconds(1))` | 工艺规定的停留时长，不能代替设备完成证据 |
| `with with_control(...):` | 持续行为的作用域，子树完成后执行契约退出协议；S01不用此节点 |
| `fail("id", "E_CODE")` | 业务失败，触发停止与清理 |

repeat的两种形式是同一节点，共八类；内部运行器仍可有等待状态，但不暴露为工艺步骤。`process`是外壳，`case/otherwise`是分支字段，payload、calibration、subject_id和items_at是数据表达式，不是设备行为。

只允许固定with块、叶节点及受控表达式；禁止任意Python函数、async、导入、赋值、for/while/if、回调或任意对象方法。源码只解析为控制树，不由Python解释器执行。

步骤ID在流程内唯一，建议“目的_编号”。编号不决定运行顺序；结构才决定。重复激活还需run、iteration_path、activation_id、request_id，不能复用上轮Done。

## 3. invoke的自动生命周期

`invoke`不是“发送命令后立即返回”。每次调用导入以下义务：

```text
校验行为和输入 → 获取有效条件快照 → 原子授权并提交请求
→ 确认本次请求接受 → 监测持续条件 → 确认本次结束证据
→ 完成交接和清理 → 后继节点可执行
```

- 前置条件来自`condition_contract.preconditions`；假或未知时不提交命令，并受准入期限约束。
- 持续条件来自`sustaining_conditions`；只在适用阶段检查，不能要求已消费的前置条件永远为真。
- 结束条件来自`completion_contract.checks`，必须关联本次接受的请求及物料身份；初始空闲、旧Done、计时、动画进度均不能作为本次成功。
- 超时、失败、取消分别进入停止与资源处置。尚未确认实际停止不能释放运动资源或报告完成。
- 输入命令值不等于实际反馈。条件可能需要信号、实际位置、支承、库存和交接记录共同判定；不能把缺失观测默认为True。

编译绑定检查必须追溯“实例 → DeviceSpec版本 → behavior_id → 条件key → 提供者 → 信号路径及观测来源”。条件映射缺失应报错，提供者未实现应阻塞。现有检查报告中的`automatic_obligations`列出逐调用导入的前置、持续和结束条件，便于审核；它不是已执行的PLC程序。

运行期限在`bindings.process_contract`统一声明，包括准入、接受、执行、停止、库存快照及最终验收期限。具体设备适配需要更严格限值时再明确绑定；不能因移除显式等待而变成无限等待或无条件推进。

## 4. 行为、参数和载荷

行为必须存在于设备`transport_behaviors`，不允许别名猜测或“候选能力”占位。invoke只允许可调度且有限结束的action/composite/service；internal、observer、passive及continuous行为不可作为一次性invoke。

普通关键字严格匹配`arguments_schema`的必需项、类型、单位、范围和适用配置。空schema不代表具体模型的命令无需载荷。

```python
invoke("pick_place_A_013", R1, "pick_and_place",
       payload=payload("R1.pick_and_place",
                       material=a.material, source=a.source, target=C2.entry))
```

`payload`是独立于标量参数的保留字段。`R1.pick_and_place`引用同名的单动作载荷绑定，锁定实例、行为和版本；其中的material/source/target是类型化对象与位置，不是给设备增加新的行为参数。S01仍标为pending_model_adapter，未选择具体命令schema，不能直接声称符合robot-command@1或可发给PLC。

两种只读数据引用：

```python
calibration(C1, "pitch_m")   # 从实例标定表取得带m单位的节距
subject_id(a.material)      # 从冻结身份表取得契约要求的DINT编号
```

标定必须声明单位、范围、有效值及状态。S01节距仍为null/pending_calibration，不填猜测值，运行前必须补齐。身份表使用一一对应的1～2147483647编号，0保留；不允许直接拿字符串冒充subject_id。表只编码身份，不组织工艺。

## 5. 持续动作与有限动作

连续运行的`start_conveying`没有单次Done，不能简单改写为invoke来消除等待。需要“移动一段距离并停稳”时，设备契约必须真正定义该有限行为。

传送带契约1.1.0增加可选复合行为`move_by_distance(distance_m)`，并同步登记到[原始行为规范](../../docs/schema.md)：

- 命令距离绑定`target_distance: REAL`，单位m，接受后冻结；速度取有效实例参数。
- 进入前要求连续整带模式、定距与位置观测能力、有效标定、设备停稳、载荷/空间授权及相关机械臂退位。
- 内部组合已登记的start_conveying和stop_conveying，使用本次编码器基准及制动模型。
- 完成必须同时确认表面行程、实际停稳、参与载荷的真实目标位置及支承；编码器到数不证明托盘到位。
- 取消或失败必须受控停止。该行为仍为pending_adapter，不能自动推定Conveyor_aankws已有定距能力。

`transport_to_exit`只确认指定物料到达出口；`release_material`确认下游交接；`stop_conveying`确认实际停止。三个动作语义不同，S01明确按顺序调用，未改变既有行为的完成含义。

## 6. 集合、并行与独立验收

`items_at(station, category="A")`激活时由集合提供者自动检查工位停稳、托盘身份和库存快照，再冻结成员和顺序。已知空工位可返回空集合；未知必须阻塞并受超时约束，不能当空集合跳过。

count和limit需可静态求值，范围0—10000；batch计数必须与清单一致。循环变量只在当前子树内有效；即使count=0或集合为空也校验子树的名称与类型。

par只表示允许并发，不绕过资源和几何互锁。各分支内seq按契约完成推进；全部分支完成后才进入下一拍。任何分支失败后停止新提交、取消兄弟分支并确认停止；已经发生的物料交接不回滚。

exclusive分支要求同一快照中所有条件已知且恰有一个真；多真冲突，未知等待，全假才otherwise。ordered按顺序选择首个真，更早条件未知则阻塞。选择后不改选，分支失败不尝试其它分支。业务分类可以用条件表达式，但不能用它重复设备自身的前后置门控。

流程子树结束后自动执行`process_contract`收尾：独立goal monitor核对`task-spec.json`的身份、数量、交接、空盘出线、工具为空、驱动停稳及请求/资源清理。控制树走完不等于整批成功。最后一盘的外部移出若尚未确认，仍处于收尾阶段。

时钟保持一致快照、反馈归并、持续条件/取消/超时、候选、仲裁提交、物理推进的顺序。后继最早下一tick提交；有效完成证据与期限同tick时先检查完成，持续条件失效优先于成功。仿真暂停冻结时钟。

## 7. S01的简洁工艺

主线移动一个标定节距并停稳 → 两工位并行 → 每件取放、退位、运输至出口、下游交接、停带 → 下一拍。

三盘十二件，共五拍：P01/A → P02/A与P01/B → P03/A与P02/B → P03/B → 最后一盘出线。第二、第三拍两台机械臂处理不同托盘。N+2只在两工位共同节距与入口每拍至多一盘的几何和供料条件成立时适用，不是按计时推进位置。

主线准入中的入口供盘、出口清空和机器人退位，绑定到`move_by_distance`的前置条件；其结束条件承担到站与停稳。外部供料/接盘服务仍须实现，不能因脚本简短而删除外部物理事件。批次和独立目标保持不变。

完整源文件：[processes/S01/process.py](../processes/S01/process.py)。场景中没有单独的条件等待步骤，也没有把这些步骤改名藏到batch里。

## 8. 当前实现边界

```powershell
python -B tools/compile_declarative.py processes/S01/process.py
python -B tools/check_flows.py
python -B -m unittest discover -s tests -p "test_*.py"
```

`syntax_valid`表示可解析；`declaration_references_valid`表示声明引用、参数及自动条件绑定一致；`contract_binding_valid`仍会被缺少的模型载荷适配阻塞；`executable`当前保持false。静态检查不证明信号已经被求值、物理运动可行或并行时间已经重叠。

0.3自动门控检查覆盖十二场景的声明、标定、身份表、库存、循环交接及最终验收；加工设备只做实验定义引用检查，仍拒绝标准准入。完整运行调度、设备适配、几何标定及PLC后端仍需实现，禁止通过删除条件检查获得可执行标记。

## 多场景数据与交接规则

batch.jobs和batch.pallets均为有限清单；select按声明字段筛选，chunks分组，嵌套pallet.items仍使用repeat。batch_field_types显式登记字段含义，检查器核对真实记录、引用、类型及循环上限，不能靠字段名猜测物料或位置。

quantity允许包装已检查的数值字段，例如quantity(job.height,"m")；转台角度使用契约的°，不能直接把rad数值传入angleTag。

换盘、载具批组及共用进出料位置需要iteration_contracts，分别描述当前身份的外部准入和交接收尾，不包含设备动作序列。它们是过程生命周期义务，不是设备固有信号，也不表示已有事件实现；未知时阻塞。S02每组三盘的填充/排空仍显式写在DSL。

加工设备继续保留ExperimentalAssetContract。静态检查核对其中的行为名、参数、配方及原始条件来源；experimental_condition_bindings保留原条件树用于审核。声明引用可检查，但标准契约准入仍报告EXPERIMENTAL_BEHAVIOR_NOT_ADMITTED，不提升为可执行或标准设备。

S12将A面加工、松夹与转位交接放入同一顺序分支，不能依靠去掉显式等待来推测加工已经完成。其它跨设备到位与容量依赖由行为契约及场景互锁提供者确认；完整资源仲裁、几何与物理执行仍须集成验证。
