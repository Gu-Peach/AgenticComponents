你现在卡住的地方，确实是前面框架中的一个问题：我们把“理解场景”“拆解工步”“行为对齐”画成了三个独立步骤，但它们实际存在相互依赖。

**更合理的方式是：先建立场景的基本认知，再带着工艺目标查询和理解相关部分，在这个过程中逐步形成工步并绑定行为。** 工步拆解与行为绑定可以交替进行。

这里最需要先澄清的是：**“理解场景”究竟要求智能体知道什么。**

**1. 对你的研究而言，理解场景就是建立“可以怎样操作这个场景”的认知**

看到图中有两台机械臂、几条输送线和一个托盘，只完成了对象识别。面向工艺规划，还需要回答：

| 理解层次       | 智能体应能回答的问题                                     |
| -------------- | -------------------------------------------------------- |
| **对象与位置** | 场景里有什么？物料在哪里？它属于哪个托盘、哪个槽位？     |
| **设备能力**   | 哪个设备能输送、抓放、停止或交接？行为需要哪些输入？     |
| **操作范围**   | 哪台机械臂可能操作哪些区域？目标位置需要满足什么条件？   |
| **状态变化**   | 一个行为完成后，物料位置、持有关系或设备状态会怎样变化？ |
| **设备协作**   | 怎样让前一个设备的操作结果，成为后一个设备的操作条件？   |
| **约束与未知** | 哪些操作需要等待、互斥或核查？哪些信息还不足以作决定？   |

其中，**“状态变化”和“设备协作”是之前讨论里不够突出的部分。**

例如，智能体不仅需要知道“机械臂具有抓放行为”，还需要知道：

> 抓放需要有可抓取的物料和可放置的目标；执行后，物料转移到目标区域。要完成“从出料线出口交付”的目标，放到入口之后还需要输送及交接。

这才使设备能力能够参与工艺推理。

**2. 场景理解可以分为“基础理解”和“任务相关理解”**

基础理解可以提前完成，并随场景修改而更新：

- 设备、物料、载具和位置的身份。
- 设备契约及实例配置。
- 初始装载、连接和支承关系。
- 具名操作位置及坐标来源。
- 已确认的服务关系、约束和待核查项。

这些信息与具体工艺无关。例如，改变 A/B 类的出料要求，不会改变 C4 的位置，也不会改变 R1 的契约能力。

任务相关理解则在需求进入后开展。例如，目标是“把托盘中的 A 类物料交付到 C4 出口”，此时才重点追问：

- 对应哪些物料？
- 当前物料位置是否适合抓取？
- 如果不适合，需要先怎样移动托盘？
- 哪些机械臂可以承担抓放？
- C4 的合法放置区域在哪里？
- 放置后还需要哪些操作才能完成交付？

**因此，场景理解由任务引导，但不以一份已经完整拆好的工步方案为前提。**

**3. 工艺文档首先解析出“目标和要求”，随后结合场景细化工步**

你说的“先解析工艺方案，拆出工步”，需要根据文档详细程度处理：

- 如果文档已经规定具体工步，就提取并核查这些工步。
- 如果文档只说“完成分类拆垛”，就只能先提取对象、分类规则、目标和约束，具体工步需要结合场景生成。

对你的场景，可以采用下面的推理过程。这里描述的是一种规划方式，具体可行性仍依赖已确认的场景信息。

| 当前规划问题             | 需要理解的场景信息                       | 得到的规划结果                           |
| ------------------------ | ---------------------------------------- | ---------------------------------------- |
| 要处理哪些东西？         | 托盘、物料身份、槽位和类别               | 确定任务对象集合                         |
| 能直接开始抓取吗？       | 物料当前位置与机械臂服务范围             | 若当前不满足抓取条件，则增加托盘入站任务 |
| 托盘应该停在哪里？       | 分拣位置、支承条件、相关机械臂的服务关系 | 绑定托盘目标位置及到位要求               |
| 谁将物料放到哪里？       | 机械臂能力、抓取参考、出料线放置区域     | 选择抓放设备并绑定源与目标               |
| 放到输送线上就完成了吗？ | 需求终点是入口、出口还是接收方交付       | 决定是否还需输送和交接                   |
| 何时移动空托盘？         | 物料处理结果、机器人退位与主线条件       | 建立分支汇合及空盘退出依赖               |

这里，**新工步的产生来自“目标尚未满足，而现有状态与目标之间还差什么”。**

不是先凭语言完整列出所有工步，再去寻找对应设备。每次理解到一个必要条件，都可能促使规划补充或调整工步。

**4. 应该给 Agent 什么输入**

建议给它一份可直接阅读的“场景概览”，再提供按需查询工具。

场景概览只需包含五类内容：

| 输入内容           | 建议提供的信息                                 |
| ------------------ | ---------------------------------------------- |
| **实体清单**       | 设备、物料、载具的 ID、类型及简要用途          |
| **当前或初始状态** | 物料归属、所在位置、托盘装载等，并标明快照时刻 |
| **具名位置与关系** | 入口、出口、分拣位、槽位、放置区域及已确认关系 |
| **行为能力摘要**   | 行为输入、适用条件、完成后的可确认结果         |
| **约束与未知项**   | 容量、耦合驱动、共享空间，以及需要查询的关系   |

其中，行为能力摘要最好明确为：

```text
设备与行为：某机械臂的 pick_and_place

输入角色：
物料、源位置、目标位置

适用条件：
物料可抓取、工具可用、目标可放置、服务关系满足要求

完成结果：
本次物料已释放并获得目标支承等完成证据

需查询的信息：
源与目标的具体位姿、可达性及相关空间条件
```

这层“条件—结果”摘要需要从已有契约和实现中审核整理。你目前的契约已经提供条件与完成检查，但用于规划的统一结果语义仍需要进一步明确。

Agent 再按需调用：

- 查询某设备及其行为详情。
- 解析某对象的实际操作位置。
- 查询或核查设备对某源/目标区域的服务关系。
- 核查放置、支承、载荷和交接条件。
- 查询对象状态或指定工步的验证结果。

这样，Agent 获得的是**可用于决策的事实与能力**。不必一开始读取所有网格顶点、关节矩阵和每个信号，也不必仅凭截图估计精确距离。带实例标签的三维视图可以辅助理解布局、消解指代，精确判断通过结构化数据和工具支持。

**5. “工步对齐”应成为规划过程的一部分**

建议将实际过程理解为：

```text
场景基础信息 + 工艺目标
          ↓
识别当前需要解决的操作目标
          ↓
查询相关对象、位置、设备能力与条件
          ↓
提出候选工步并绑定设备、对象和位置
          ↓
核查能否衔接、还缺少哪些前序操作
          ↓
补充或调整工步，逐步形成完整方案
```

例如，“将物料交付到 C4 出口”先绑定了对象和目标，但暂时没有绑定全部执行行为。查询场景后，才确定需要哪些抓放、输送和交接行为。

所以前面讨论的“四类对齐”仍然有用，但它们应当支持**逐步绑定**：有些对象和位置可在需求解析后立即确定，行为组合及部分位置则在规划过程中进一步确定。

**6. 怎么证明 Agent 理解了场景**

不建议用“能描述这张图”作为主要依据。可以通过可观察的决策检验：

- 给定某个物料和目标，它能否找出正确的设备与操作位置候选，并说明依据？
- 给定一个操作目标，它能否识别必须先满足的条件，补出必要的前序工步？
- 改变设备布局后，它能否重新核查受影响的关系，而不是照搬原工艺？
- 同一场景改变分类或目标要求后，它能否生成不同方案，同时保留正确的场景事实？
- 缺少位置、能力或交接证据时，它能否指出缺失项，而不是编造一个确定答案？

这些可以分别评价**位置绑定正确率、候选能力正确率、必要前序识别率、场景变化后的规划适应性，以及未知识别能力**，再用执行验证检查最终方案。

据此，你的三个子研究点可以更清楚地定位为：

- **2.1 建立面向操作推理的场景与需求表示**：让信息能够支持“条件—操作—结果”的推理。
- **2.2 研究任务驱动的场景理解与逐步工步规划**：一边查询核查场景，一边分解目标、绑定行为和补全依赖。
- **2.3 将已明确的工艺方案转换为 DSL**：保持设备、对象、位置与控制关系的一致性。

**“理解场景”的关键成果，是能够依据场景事实推理出一项操作如何实现、需要哪些前提、会产生什么结果，以及如何与下一项操作衔接。** 这为研究点二提供了比“识别场景对象”更明确、也更可验证的研究对象。
